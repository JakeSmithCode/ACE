Orientation and guardrails for working in this repo. Read this before changing engine or contract code.

## What ACE is

An asynchronous, server-authoritative Valorant esports management sim. You own a club; you set rosters/comps/tactics ahead of time; a deterministic engine resolves every scheduled match on a tick; you watch matches back on a 2D viewer. A match is a pure function of `(rosters, tactics, patch, seed)`, so "live" and "replay" are the same stored data, and any round can be rewound and re-simulated. Full design: `docs/DESIGN.md`.

The bet: we don't compete on 3D fidelity, we compete on **interrogability** — a tactical instrument you can rewind, fork, and x-ray.

## The one rule that everything depends on: determinism

The engine is pure. Same input → byte-identical output, forever.

- **No `Math.random()`. Ever.** Use the seeded PRNG in `packages/engine/src/rng.ts` (mulberry32). Thread the `Rng` instance through; never create a second source of randomness.
- **No `Date.now()`, no `performance.now()`, no wall-clock, no I/O** inside `simulateMatch` or anything it calls.
- **No iteration-order nondeterminism.** Don't rely on `Object.keys` order across engines, `Set`/`Map` insertion quirks, or floating-point that varies by platform in a way that branches the sim. Sort explicitly where order matters.
- If you add a system that needs "randomness," it draws from `rng`. If it needs "time," it uses the round's normalized `t` (0..1).

**How to verify after any engine change:** run `pnpm sim -- --seed 42` twice and diff the output — it must be byte-identical. Then run a spread of seeds and confirm every match completes (a side reaches 13) and the ending-method mix looks sane. Determinism breaking is the highest-severity bug in this codebase; it silently kills replays, debugging, and server resolution.

## The spine: the timeline contract

`packages/shared/src/timeline.ts` defines `MatchInput` → `MatchTimeline`. The engine emits it; the viewer reads it. Neither side may know anything about the other beyond this shape.

- Treat the contract as an API. Changing it is a real decision, not a convenience — it ripples to the engine (producer) and the viewer (consumer) at once.
- Adding a field is usually safe (consumers ignore unknowns). Changing/removing a field, or changing the meaning of `t`, is breaking — update both sides and bump thinking about `version`.
- Event `t` is normalized 0..1 within its round. Keep it that way.

## The map pipeline (and why it's elegant)

A map's official minimap (`displayIcon`) is also its collision data: the alpha channel is the walkability mask — opaque = floor, transparent = wall. `packages/maps`:

- `scripts/build-navmesh.ts` reads alpha → a coarse walkable grid → `data/<map>.navmesh.json` (and a copy in `apps/web/public/` for the viewer).
- `src/navmesh.ts` runs A* on that grid (`pathfind`), plus the LOS/vision primitives (`losClear`, `inView`).
- To add a map: drop its `displayIcon` in `assets/` (and `apps/web/public/` so the viewer can show it), add anchors in `src/anchors.ts`, rerun `pnpm navmesh:all`. No hand-tracing. Everything downstream (routing, vision, future heatmaps) operates in the same 1000×1000 image space, so it all lines up for free.

**All 11 official maps are in** (navmesh + anchors): ascent, abyss, bind, breeze, fracture, haven, icebox, lotus, pearl, split, sunset. `pnpm sim -- --map <id>` resolves any of them; the viewer loads assets by `timeline.map`. But **only Ascent's anchors are tuned** — the rest are first-pass `atkSpawn`/`mid` eyeballed from the asset pack's site centers, so they complete + render but play unbalanced. Two known causes to fix when tuning: (1) `SPEED`/`ROTATE_SPEED` are calibrated to Ascent's scale, so far-apart-site maps (fracture, bind, breeze) let attackers plant before rotations land → detonation-heavy/attacker-sided; (2) `MapAnchors.sites` is `{A,B}` only — Haven and Lotus field two of their three sites until the engine models N sites (`siteBias`/`read` are binary today). Don't assume a non-Ascent map is balanced.

When you touch geometry, reuse these primitives — don't write a second raycaster or a second notion of "walkable."

## Current state

Phase 0 (the keystone) works: a real deterministic engine producing full matches, the map pipeline, and a viewer rendering it on the actual Ascent minimap.

Vision is now wired end to end (roadmap step 1, done): agents have a facing and a ~120° awareness cone; `inView()` composes that cone onto the alpha-mask LOS; a duel only resolves if someone sees the other, and spotting an unaware enemy first is decisive. The viewer renders each agent's wall-clipped vision cone by raycasting the same navmesh. This is correct — keep building on it. Backstabs, off-angles, and retakes should emerge from geometry, never from hand-authored exceptions.

Utility is in (roadmap step 2): abilities fire for real and bend duels through the same geometry — no hand-authored exceptions. Controllers throw `Smoke`s (vision-blocking circles over time); initiators/attacking-duelists throw `Pulse`s (recon/flash that grant the first shot in an area-window). **Smokes are directional: an enemy smoke on the sightline blinds that viewer, never the side that threw it** (`blindedThrough()`). This is the load-bearing decision — it's what makes the `utility` attribute a net positive instead of self-harm (an earlier symmetric model made higher utility *lose* more). Reach/duration scale with the caster's `utility` (0..1), so the stat expresses through play. If you extend utility, preserve that invariant: more utility must help its owner.

Match-night form is in (the match-expression layer of the three-layer model). Each player draws one form edge per match (`FORM_SWING`, in `simulateMatch` so it's held all match), added to their duel edge — same roster, different night. Drawn in a fixed team/player order to stay deterministic; if you add draws before it, the whole stream shifts (that's fine, just regenerate the sample). Keep it bounded and *fair* (DESIGN §2/§18: a bust is a risk you took, never the dice mugging you). The viewer shows it live via the scoreboard (K/D tallied from kill events — no contract change). The third layer's missing piece, *potential behind fog*, belongs to scouting/management (Phase 3), not the engine.

True Odds is in — the determinism thesis turned into a feature. The round resolution is now a pure function, `resolveRound(agents, smokes, pulses, nav, …, rng)`, split out from setup. `simulateRound` runs it once canonically on the **match rng**, then `FORKS` (120) more times on *throwaway* agent copies seeded by `forkSeed(seed, n, i)` to measure how often the attacker wins — the round's `winPct`. **The forks must never draw from the match rng** (that's why they get their own `new Rng`); this is what keeps the canonical timeline byte-identical. `winPct` is additive on `Round` (version stays `1`); the viewer plots it. If you change setup-time rng draw order, regenerate the sample.

Tactics is in — the manager's lever, and the bridge to the management game. `MatchInput.tactics?: [Tactics, Tactics]` (the type lives in `@ace/shared/models`). The round *resolves* it: attacker `siteBias` weights site choice; `tempo` scales attacker arrival + execute timing; defender `read` decides where bodies pre-commit (they set up on the read, **not** the actual site, so a wrong read is paid for in rotation time — rotators move at 0.6 speed and arrive late); `aggression` pushes mids forward and trades the held-angle `holdBonus` for early picks. The attacker-site-vs-defender-read mind-game is real (~7pt round swing on identical rosters; verify by holding rosters equal and flipping only the read). **Every team always has tactics**: owners author their own; a club/bot without them falls back to `DEFAULT_TACTICS` (in `@ace/shared`, so the engine and the future management layer share one default). Tactics is an engine *input* — it does not touch the `MatchTimeline` contract or the viewer.

Per-player attack roles are in (the seed of the tactics editor). `Tactics.attack.entry` (player id) leads the push — arrives 15% sooner, takes opening contact; defaults to `bestEntry` (highest entry attr) if unset. `Tactics.attack.lurk` (player id, opt-in) peels one player off the execute to a flank hold (`lurkPt = lerp(mid, otherSite, 0.4)`, facing the rotation), trading a softer 4-player hit for flank picks + a late man-advantage. The lurk is a deliberate **tradeoff** (~even win rate, ~0.3 flank kills/round) — tune `lurkPt`/arrival if you want it stronger, but keep it a choice, not a free win. Elevation decision: **stay 2D** — walls are already enforced by the alpha mask; a per-map height layer is deferred until a genuinely vertical map needs it.

Authored plays + kill points are in (the engine half of the cs-manager-style editor). `Tactics.defense.play?: Play` (in `@ace/shared/models`) lets an owner place defenders **exactly** instead of leaving them to the procedural read: `Play.plans` is one `PlayerPlan` per player — a `pos` to hold, plus an optional **kill point** `rotate: { pos, onDeathOf }` that re-routes that player when a named teammate dies. The engine resolves it in two places: setup branches on `defTac.defense.play` (authored agents spawn at `plan.pos`, `anchor: true`, with `rotatePlan` resolved from the trigger player id → handle via `byId`; a planless player falls back to holding the site); and the kill-resolution loop in `resolveRound` fires the trigger — when `loser.handle` matches a live agent's `rotatePlan.onDeathOf`, it re-paths that agent (`pathfind` → `rotate.pos`, `departT = t`, `arrive = arriveTime(path, ROTATE_SPEED)`, then clears `rotatePlan`). This **reuses the `departT` hold-then-move machinery** info-gated rotations already gave us — a kill point is just a hold whose release trigger is a teammate's death instead of contact, so it costs no new viewer contract (still `version: 1`, the rotation rides the existing `move` event). The fork clones preserve `rotatePlan` (spread, and forks run before the canonical pass) and reset `exposedUntil`/life, so True Odds stays byte-identical and the authored play stays dormant when unset (seed 42 unchanged). It's a **reactive** play: lose the bait and the team collapses onto the kill point, so a wrong trade is punished by geometry, not a scripted exception. v1 is hold + one conditional rotation; the natural extensions are more triggers (`onContact`, at-time), attack-side plays, and N-step chains.

Routes are in (the path, not just the endpoint — works for both sides). `PlayerPlan.route?: Vec2[]` is the ordered waypoints walked **into** the hold: `[...route, pos]` is the full path the engine builds, so an empty/absent route means "start already on the hold" (the original byte-identical behaviour). An authored defender with a route departs at 0 and walks it at normal speed (`arrive = arriveTime(path)`), so a **longer route is a real tradeoff — the player is set up later**. This needed no new viewer contract and no new playback code: `posAt`/`facingAt` (engine) and `posWithDepart`/`facingOf` (viewer) already operate on the `path` array, so a multi-waypoint route just rides the existing `move` event (still `version: 1`). The fork clones share the `path` ref but only ever reassign it (never mutate), so True Odds stays byte-identical and routes stay dormant when unset (seed 42 unchanged). The browser editor draws them: pick a player, click the map to drop waypoints (spawn→hold, in order), drag to move, click to remove — every edit re-sims live. The editor also reads the navmesh for **walkability feedback**: a hold/waypoint on a wall gets a red ring and a verbatim route segment that clips a wall is drawn red (an *un*-routed kill-point rotation is A*'d by the engine, so its straight intent-line is deliberately *not* flagged — only authored verbatim paths get the wall check). **Kill points are routable too**: `rotate.route?: Vec2[]` authors the rotation's path — when the trigger fires the engine walks `[here, ...rotate.route, rotate.pos]` verbatim, else it falls back to `pathfind` (so an unrouted kill-point stays byte-identical). The fork clones spread `rotatePlan` (route included, by ref, only ever reassigned) so True Odds is unaffected. **Routes are capped** at `MAX_ROUTE_WAYPOINTS` (5, in `@ace/shared`) — a play is a *sketch*, not turn-by-turn micro; the editor enforces it (each of a player's hold route and kill-point route gets its own budget) and the engine stays agnostic to length.

Authored facing + kill-point triggers are in (the "quick wins" pass). `PlayerPlan.face?: Vec2` is a point the defender watches from the hold — the engine sets `holdDir = face ? unit(pos, face) : unit(pos, atkSpawn)` (default unchanged), so authoring an angle is a real off-angle/crossfire lever and rides the existing `move.hold` (no contract change; the viewer already renders facing). And the kill point's release is now a tagged trigger, `rotate.trigger: RotateTrigger = {kind:'death',player} | {kind:'contact'} | {kind:'time',t}`: **death** is the classic bait (fires in the kill loop when that handle dies), **contact** fires when `contactT` is set (first kill or an attacker reaching the site — reuses the info-gate signal), **time** fires when the round clock passes `t`. The last one *is* the timing lever — a hold at mid with a `time` trigger to the site is a staggered "hold then fall" default, no new machinery. All three are resolved by one `fireRotation` closure (walk the authored route verbatim, else A*), so contact/time triggers reuse the exact `departT` hold-then-move path the death trigger and info-gated rotations already share. Forks spread `rotatePlan` (trigger by ref, only reassigned), and every field is opt-in, so True Odds and seed 42 stay byte-identical. The editor exposes facing as a draggable nub per defender and the trigger as a kind-picker (+ a teammate select for death, a time slider for time). Next on the same primitives: N-step chains and attack-side plays.

Attack-side plays are in — the other half of the editor, where routes + triggers + lineups converge into an authored execute. `Tactics.attack.play?: Play` mirrors the defense play: per-player `pos`/`route`/`face`, a push `rotate` (a lurk that flanks on a death/contact/time trigger), and attack `lineups`. Three attack-specific bits: (1) `Play.site?: 'A'|'B'` **forces the round site** — `site = atkTac.attack.play?.site ?? (rng roll)`, so the rng draw only happens when unforced and the no-play sample stays byte-identical; (2) authored attackers spawn at a **deterministic per-index spread** off `atkSpawn` (no rng) and are A*'d to their spot when unrouted, walked verbatim when routed (same rule as defenders, but defenders start *on* the hold while attackers travel from spawn); (3) the default facing is **forward** (`unit(spawn, pos)`) not toward-spawn. The trigger resolution (`resolveTrig`) and the lineup builder were generalized to both sides — lineups now carry their `side` (attack smokes blind defenders, defense smokes blind attackers; `blindedThrough` holds), and a caster on either side skips their procedural auto-cast. Every field is opt-in (NCT/MRD ship no `attack.play`), so seed 42 is byte-identical. The editor authors it through the **same `PlayEditor`** (a `mode` prop flips the facing default + adds an A/B site picker); each team now has an `attack` and a `defense` play button. Verified: an A-execute forces site A:12/B:0 and moves the score; forcing B with A-positioned players tanks it (positions must match the site — the owner's call, like a hold in a wall).

Utility lineups are in (the manager authors the util, not just the positions). `Play.lineups?: Lineup[]` — each is `{ player, kind: 'smoke'|'flash'|'recon', at: Vec2, t }` — feeds the **same** `smokes[]`/`pulses[]` geometry the procedural utility builds, so an authored smoke blinds attackers through it (the `blindedThrough` side invariant holds: defensive `side`, blinds the enemy) and a flash/recon grants the defender the first shot in its window. Reach/duration still scale with the caster's `utility` stat (`SMOKE_R + SMOKE_R_UTIL*u`, etc.), so the stat stays meaningful. **A lineup replaces that caster's automatic cast** — `authoredCasters` is collected first and skipped in the procedural loop, so you don't get double utility from one player; players you don't author keep their auto-cast. Lineups draw **no rng** (the point and `t` are authored, reach is a pure function of the stat), so they don't perturb the rng stream — forks and canonical use the one array built before the fork loop, and seed 42 stays byte-identical (no play → no lineups). They ride the existing `ability` event (no contract change; the event has no position, so the *match viewer* doesn't draw the cloud — but the **editor** does, since it owns the `Lineup` data: a draggable center + a translucent reach circle whose radius mirrors the engine, plus a caster select and a time slider). v1 is defensive (lives on `Tactics.defense.play`); attack-side lineups come with attack-side plays.

Trading is in (round dynamics 1 of 3). `duel` now takes a numeric `surprise` edge (not `-1|0|1`); resolveRound composes it from vision (`±FIRST_SHOT`), pulses (`±FIRST_SHOT`), then a **trade**: a kill sets `winnerAg.exposedUntil = t + TRADE_WINDOW`, and a teammate who can see that exposed killer gets `±TRADE_EDGE` (via `Math.max/min`, so it flips a held first-shot but never weakens a bigger same-side edge). `exposedUntil` must reset to `-1` in the fork clones (it does) or odds drift. Trading favours the grouped side (~+13pt to attackers), and ~37% of kills get traded. Viewer tags trades in the kill feed (⇄) — derived from the event stream, no contract change.

Modeled retake is in (round dynamics 3 of 3). Post-plant, a defender within `DEFUSE_R` of the spike (`plantPos`, captured at plant) with no attacker within `SITE_R` channels a **defuse**; `DEFUSE_TIME` of uncontested time wins it and finally emits the long-dormant `defuse` event (the viewer renders it). Crucially the hold edge **inverts** post-plant: `duel` now takes an explicit `holdEdge` (not `def.holdBonus` internally) and resolveRound passes `planted ? -POSTPLANT_HOLD : d.holdBonus` — so attackers hold the crossfire after the plant, defenders push in. That inversion (POSTPLANT_HOLD=10) is what rebalanced the retake (which alone over-helped defense to ~41%) back to **~49% attacker, ~6% stalls** with all three dynamics in. Note `SPIKE_TIME` doesn't bind (rounds resolve before detonation) so it's not a balance lever — `POSTPLANT_HOLD` is. With trading + info-gating + retake all in, the canonical sample was regenerated again.

Info-gated rotations are in (round dynamics 2 of 3) — the defensive counterplay to trading. Agents gained `departT` (when they start moving; `Infinity` = holding for info). Anchors and attackers depart at 0; **rotators hold their read** (`departT = Infinity`, watching their lane from `st.from`) until **contact** — the first kill (`hadKill`) or any attacker within `SITE_R` of the site — then `departT` is set to that `t` and they rotate at `ROTATE_SPEED` (0.85, faster than the old 0.6 since they now move with purpose). `posAt`/`facingAt` hold at `path[0]` until `departT`. This rebalanced trading back to ~47% attacker and cut stalls (time%) from ~11% to ~7%, so `HOLD_BONUS` went back to its original 6 (the 9 was a temporary patch). **Contract: the `move` event gained `departT`** (additive, version stays 1); the viewer mirrors the hold-then-rotate via `posWithDepart`. Note: the hoped-for "fast hit punishes a wrong read harder" interplay came out ~tempo-flat (rotation delay scales with contact either way) — parked as future tuning; the read itself is still a strong lever. Tuning knobs: `TRADE_WINDOW`, `TRADE_EDGE`, `ROTATE_SPEED`, `HOLD_BONUS`.

Comp is in — the other half of "what you field." `MatchInput.comp?: [Comp, Comp]` maps player id → agent; a player not listed falls back to their **top-mastery agent** (`topAgent`), so every team always has a comp. Per match, `addLoadouts` builds a `Loadout` per player: the fielded agent's **role** (via `AGENT_ROLES`) decides the kit fired in the utility loop (so comp reshapes a team's whole utility profile), a `compEdge` (~±5, from the agent's patch `tier` and the player's `mastery`) adds to the duel, and `utilFactor` scales their utility by mastery. Loadouts are built once per match and threaded into `simulateRound` like `form`. Fielding mastered meta mains beats off-pool picks ~88% of matches (identical rosters). The fielded agent is surfaced additively on `PlayerMeta.agent` (version stays `1`); the viewer shows it on the scoreboard. **Engine assumption: player `handle` is unique within a match** — kill events, `form`, and `loadouts` are all keyed by handle. Real orgs have distinct handles; if you ever synthesize teams, give them unique handles or these maps collide.

Economy is in — a real buy rhythm (`economy.ts`). `decideBuy(creds, opp, lossStreak)` reads our bank, the enemy's, and our streak; the key behaviour is **saving** (eco to bank a real buy rather than half-buy into rifles). `nextCreds` now **spends the buy** (`COST` per tier) then earns (win 3000 / loss bonus 1900·2400·2900 / +200 a kill / +300 for a plant), clamped 0..9000 — so buys actually drain and a buy-and-lose streak bleeds you toward an eco. Buys feed weapon `TIER`, so an eco is a weaker round (shows up as a low `winPct`). It's engine-internal (not a manager input — in-game money is an in-game call); no contract change. The viewer shows each team's buy on the scoreboard. Tactics, comp, and economy all changed the canonical stream; the committed sample was regenerated (seed 42 is now 23 rounds / 164 kills).

## The engine runs in the browser (tactics editor)

`simulateMatch(input, nav, forks?)` is **pure** — the navmesh is injected, not read from disk — so the same engine runs client-side. To keep it browser-bundleable: `packages/maps/src/index.ts` is a **pure barrel** (geometry only); the node-only `loadNavmesh` lives in `load.ts` and is imported **directly** (`cli.ts` does a relative `../../maps/src/load.js` import) so it never reaches the web bundle. The web app depends on `@ace/engine` + `@ace/maps`; `apps/web/src/App.vue` fetches the navmesh, builds a `MatchInput` from the exported sample, runs `simulateMatch` live, and re-sims on every control change (`FORKS=50` there for snappiness; the CLI stays 120). **Determinism holds across runtimes** — seed 42 gives the same 13–5 in node and the browser; if it ever doesn't, suspect a non-deterministic JS op (Date, Math.random, iteration order), not the seed. The committed `timeline.json` is still the CLI artifact but the viewer no longer needs it (it sims live).

## The world layer (`@ace/world`) — Phase 1 begins

`@ace/world` is the persistent-world core: it generates a league and resolves a season, and it is **pure and deterministic exactly like the engine** (same `Rng` from `@ace/engine`, the navmesh injected, no `Date`/`Math.random`/I/O). A whole season is a function of one seed. This is deliberate: the **single-player loop runs it client-side now, and the Phase-2 server worker will run the same code** to resolve scheduled ticks — no fork, no rewrite.

- `clubs.ts` — `makeLeague(seed, n)` → `Club[]` (`{ team, tactics, strength }`). Rosters are role-shaped (`ROLE_SHAPE` biases each role's attributes so identity is legible in the stat line), handles are drawn **without replacement** from a global pool (the engine assumes unique handles within a match — keep them globally unique so cross-club matches never collide), and strength descends across the field with noise (a hierarchy, not a fixed ladder). `makeTactics` varies the dials around sane ranges so AI orgs feel distinct.
- `schedule.ts` — `roundRobin(n)` / `doubleRoundRobin(n)` via the circle method (n even). A season is `Matchday[]`, each a set of `{home, away}` club-index fixtures.
- `season.ts` — `resolveFixture` runs `simulateMatch` (no stored timeline; a fixture's `seed = fixtureSeed(seasonSeed, day, slot)` is stable, so the web app **re-sims to watch**). `standings()` builds the table (points → round diff → rounds for).
- Verify with `pnpm season -- --seed 7 --clubs 8`: deterministic across runs, and the `strength→rank agreement` line should sit high but not perfect (healthy upsets). If you add rng draws to club/season generation, the whole world shifts — that's fine, just expected.
- `develop.ts` — the **off-season development tick** (Phase 1's player-model spine): `developPlayer`/`developSquad`/`developLeague(clubs, rng)` age every player a year and move their **current** ability toward their **potential** (per-attribute ceilings generated in `makeClub`, hidden from the manager — Phase-3 scouting). It encodes the esports aging curve (DESIGN §4.4): teens close ~⅓ of the gap-to-potential a year, the early-20s peak, then decline past peak — **mechanical** attrs (aim/movement/entry) fade earlier and faster than **cerebral** ones (gameSense/utility/clutch), the veteran-IQ effect. Pure and deterministic (one `Rng`, fixed club/player order). `developLeague` refreshes each club's `strength` from the developed squad rating so the table reflects who grew and who aged out. Keep it **bounded and fair** (a bust is a draw you took, never the dice mugging you). Helpers `overall`/`potentialOverall`/`squadRating`/`phaseOf` are the read model the roster screen renders. Adding `potential` + its generation draws shifted the generated world (expected — the season CLI sample is re-simmed, not committed); the **match engine ignores `potential`, so seed 42 is byte-identical**.
- `market.ts` — the **transfer market** (what gives money a purpose). `playerValue` prices a player: ability is the floor, *unrealised* potential in a young player is a premium, age past peak is a discount — so a 19-year-old ceiling is the dearest thing on the board and an ageing star is cheap to buy / dear to keep. `freeAgents(seed, exclude, count)` is a deterministic per-(seed,season) pool with handles disjoint from the league (the engine assumes unique handles in a match). The per-player generator was factored out of `makeClub` into **`makePlayer`** (used by both, so a signing is the same kind of object as a homegrown player) — the extraction preserved the rng draw order, so the generated world is unchanged. Signing is a **swap**: the web store replaces your same-role player, charges the net value difference, releases the old player to the pool, and remaps tactical id references so your authored plays stay coherent.
- `transfers.ts` + the web store — the **always-open market over a flexible roster**. Your club carries a **full roster (`myRoster`, ≥5)**; the matchday five is *derived* (`startingFive` = best per comp slot, one IGL), so depth never reaches the engine (it still gets exactly 5). **Buying a player ADDS them to the roster — nobody is dropped** — at the full cash price; a club you buy from banks the fee and `backfillFor`-restocks from free agency. **Selling** releases a player for their value but is blocked when it would leave the comp short of a role (the "valid five" floor). Reserves develop and draw wages like anyone (depth costs money). AI clubs stay at five and restock from free agency when they lose a player. Every move funnels through the store; `resolveListings()` runs each match-day so a listed player can sell mid-season. The whole resolution is the shape the Phase-2 server worker will run on real bids. `aiListings(clubs, myClub)` puts each AI club's most expendable (lowest-value) player on the board; `aiWantsToBuy(...)` gates an AI club to buying only a clear upgrade it can afford. The web store reduces every move — your buy, your sale, AI churn — to one pure `trade(buyerIdx, sellerIdx, playerId)` helper (it also tracks **every club's balance**, settles them all each off-season, and runs `resolveListings()` each match-day so a player you list can sell mid-season). The whole resolution is the shape the Phase-2 server worker will run on real bids.
- `finance.ts` — club **finances** (the between-seasons economic pressure). `playerWage` is convex in `overall` (stars are dear, ~50–80% of income for a good club), `seasonIncome(rank,n)` is a sponsor cheque + placement prize, `settleSeason(team,rank,n,season)` returns the ledger the HQ adds to the balance. Tuned so a strong season funds the next and an overspending club that finishes low **bleeds** (a top squad finishing last nets ~−$6k). Pure; an economy balance pass is a Phase-6 thing.
- `scouting.ts` — **potential behind fog** (DESIGN §4.1/§5.3), the piece that makes a young signing a *gamble*. The manager never sees a player's true ceiling — only `scoutedPotential(p, owned)`: the true `potentialOverall` biased by a deterministic per-player FNV-1a `noise` scaled by `(1 − confidence)`. `scoutConfidence` rises with age (`(age−15)/13`, a realised ceiling is clearer) and with ownership (+0.26, your staff watch them daily), clamped 0.15..0.97 — so an 18-year-old free agent is the foggiest read on the board and your own veteran the clearest. `scoutedStars` is the 1–5 UI rendering. **The fog is load-bearing on price**: `market.ts#playerValue` prices off `scoutedPotential(p, false)` (the *market consensus*, fogged), never the truth — so the board's mispriced gems are exactly the kids whose true ceiling sits outside consensus, and the value never leaks the answer. Pure (no rng — the noise is a hash of the id), so it doesn't perturb the world; the match engine ignores it, so seed 42 is byte-identical.
- `meta.ts` — the **living meta** (DESIGN §7). `PatchState.agentTier` (agent → ~0.85..1.15 multiplier) is the patch; `fullPatch(base, allAgents)` gives every agent a tier, and `patchMeta(prev, rng)` rolls a new one each off-season: ~3 buffs, ~3 nerfs (a Fisher–Yates shuffle picks the touched agents), the rest mean-revert toward 1.0, returning the new patch **and** the notable `MetaChange[]` for the patch-notes feed. The tier feeds two places: `playerValue(p, patch)` multiplies by `0.55 + tier·0.45` (a buffed agent's mains are dearer — specialists track the meta), and `buildInput` threads the live `patch` into every fixture so matches reflect it too. Deterministic (the roll is seeded `seasonSeed ^ season·0x27d4eb2f`). The sharp owner reads the patch and trades on it before values catch up.
- **Roster depth + lineup (the store, not the world pkg).** A `Club.team` is *exactly five* (the engine contract). Depth lives in the web store: `myRoster` (≥5) is your full squad and the matchday five is **derived** — `startingFive(roster)` takes the best `overall` per comp slot (duelist×2, initiator/controller/sentinel×1, IGL = the starting sentinel). A buy **adds** to `myRoster` (no forced drop); `canSell` blocks any sale that would break a valid five. **Manual lineup override**: `forcedStart`/`forcedBench` (id sets) let you `startReserve`/`benchStarter` against the auto-pick — `canBench` requires another same-role player to cover, and `startingFive` falls back to a benched player rather than ever fielding fewer than five. Depth never reaches the engine (the derived five is what's fielded), so the match contract and determinism are untouched — this is the elegant bit.
- The web app reads all of this through one **store** (`apps/web/src/world.ts`, `useWorld()`) shared by the HQ/Season screen and the Tactics Editor. Your club gets two manager overlays the AI clubs don't — an authored **comp** (`myComp`) and authored **tactics** (`myTactics`) — both injected into your fixtures via `buildInput` (it clones them so the engine gets plain objects). The editor's team 0 IS your club: its dials + authored plays write straight to `myTactics`, so what you tune is what your club runs in real fixtures; team 1 is your next opponent, edited locally (non-persistent). `ROLE_AGENTS` (exported from `clubs.ts`) feeds the comp picker.
- **Don't** import `loadNavmesh` into anything the web bundles; the world CLI uses the same relative `../../maps/src/load.js` trick the engine CLI does.

## A settled contract decision (don't relitigate by accident)

Rendering vision needed facing in the timeline. The decision made: expose **only `move.hold`** — the unit heading an agent looks down once it reaches the end of its path. Facing *while moving* is the path's own direction, so a consumer reconstructs facing at any `t` from `path` + `arrive` + `hold` (see `facingOf()` in the viewer, which mirrors the engine's `facingAt()`). This was chosen over a per-tick facing track because the engine doesn't model look-arounds — sampling would just store a function the viewer can already derive. It's additive, so `version` stayed `1`. If you ever add genuine mid-path look mechanics, that's when a sampled track earns its keep — and its own `version` bump.

The viewer fetches `apps/web/public/<map>.navmesh.json` (emitted by `pnpm navmesh` alongside the engine's copy) and reuses the engine's exact LOS sampling to clip cones, so what you see matches what the engine resolved. Don't write a second raycaster.

## Tuning knobs (gameplay feel, not correctness)

These shape how lethal getting caught off-guard feels; expect to dial them after watching matches back. Keep them named constants, not magic numbers scattered in logic:

- `FOV` (cone half-angle, ~60°) — how much peripheral awareness an agent has.
- `FIRST_SHOT` — the edge for seeing an unaware enemy first; the single biggest lever on backstab/retake lethality.
- `SMOKE_R` / `SMOKE_R_UTIL`, `SMOKE_DUR` / `SMOKE_DUR_UTIL` — smoke size/duration and how hard they scale with utility; the bigger lever on how much space utility buys.
- `PULSE_R` / `PULSE_R_UTIL`, `PULSE_DUR` / `PULSE_DUR_UTIL` — recon/flash reach and window; the lever on how decisive entries are.
- `FORM_SWING` — match-night form band (± duel edge per player). Bigger = more star/dud variance night to night; keep it fair and legible, never a mugging.
- `HOLD_BONUS` + the defender rotation speed (`arriveTime(path, 0.6)`) — together the lever on how hard a wrong defensive read is punished; the heart of the tactics mind-game. Bigger hold / slower rotation = reads matter more.

To re-balance or measure a tuning change, an A/B is easy: gate utility generation, or set every non-utility attribute equal across two rosters and vary only `utility` to confirm the high-utility side wins (~58% of matches at 92 vs 18).

## Conventions

- Monorepo: pnpm + turbo. Packages are consumed as source via path mapping (`@ace/shared`, `@ace/maps`, `@ace/engine`) — tsx runs the engine, Vite bundles the app — so packages have no separate compile step; their "build" is a typecheck (`tsc --noEmit`). Don't add `rootDir`/`outDir` emit back to them, and don't commit `.js`/`.d.ts` next to `.ts` source (the web build is `vue-tsc --noEmit && vite build` specifically to avoid emitting those).
- Commit artifacts that make a cold clone work: the committed sample `apps/web/public/timeline.json` and `packages/maps/data/*.navmesh.json` are intentional so `pnpm install && pnpm dev` works without running the engine first. Regenerate them when their inputs change.
- Before opening a PR / finishing a task: `pnpm typecheck` green, `pnpm sim` deterministic across two runs and complete across several seeds, `pnpm build` green.
- TypeScript strict is on (incl. `noUnusedLocals`) — no dead variables.
