Orientation and guardrails for working in this repo. Read this before changing engine or contract code.

## What ACE is

An asynchronous, server-authoritative Valorant esports management sim. You own a club; you set rosters/comps/tactics ahead of time; a deterministic engine resolves every scheduled match on a tick; you watch matches back on a 2D viewer. A match is a pure function of `(rosters, tactics, patch, seed)`, so "live" and "replay" are the same stored data, and any round can be rewound and re-simulated. Full design: `docs/DESIGN.md`.

The bet: we don't compete on 3D fidelity, we compete on **interrogability** — a tactical instrument you can rewind, fork, and x-ray.

## The one rule that everything depends on: determinism

The engine is pure. Same input → byte-identical output, forever.

- **No `Math.random()`. Ever.** Use the seeded PRNG in `packages/engine/src/rng.ts` (mulberry32). Thread the `Rng` instance through; never create a second source of randomness.
- **No `Date.now()`, no `performance.now()`, no wall-clock, no I/O** inside `simulateMatch` or anything it calls.
- **No iteration-order nondeterminism.** Don't rely on `Object.keys` order across engines, `Set`/`Map` insertion quirks, or floating-point that varies by platform in a way that branches the sim. Sort explicitly where order matters.
- If you add a system that needs "randomness," it draws from `rng`. If it needs "time," it uses the round's normalized `t` (0..1).

**How to verify after any engine change:** run `pnpm sim -- --seed 42` twice and diff the output — it must be byte-identical. Then run a spread of seeds and confirm every match completes (a side reaches 13) and the ending-method mix looks sane. Determinism breaking is the highest-severity bug in this codebase; it silently kills replays, debugging, and server resolution.

## The spine: the timeline contract

`packages/shared/src/timeline.ts` defines `MatchInput` → `MatchTimeline`. The engine emits it; the viewer reads it. Neither side may know anything about the other beyond this shape.

- Treat the contract as an API. Changing it is a real decision, not a convenience — it ripples to the engine (producer) and the viewer (consumer) at once.
- Adding a field is usually safe (consumers ignore unknowns). Changing/removing a field, or changing the meaning of `t`, is breaking — update both sides and bump thinking about `version`.
- Event `t` is normalized 0..1 within its round. Keep it that way.

## The map pipeline (and why it's elegant)

A map's official minimap (`displayIcon`) is also its collision data: the alpha channel is the walkability mask — opaque = floor, transparent = wall. `packages/maps`:

- `scripts/build-navmesh.ts` reads alpha → a coarse walkable grid → `data/<map>.navmesh.json` (and a copy in `apps/web/public/` for the viewer).
- `src/navmesh.ts` runs A* on that grid (`pathfind`), plus the LOS/vision primitives (`losClear`, `inView`).
- To add a map: drop its `displayIcon` in `assets/` (and `apps/web/public/` so the viewer can show it), add anchors in `src/anchors.ts`, rerun `pnpm navmesh:all`. No hand-tracing. Everything downstream (routing, vision, future heatmaps) operates in the same 1000×1000 image space, so it all lines up for free.

**All 11 official maps are in** (navmesh + anchors): ascent, abyss, bind, breeze, fracture, haven, icebox, lotus, pearl, split, sunset. `pnpm sim -- --map <id>` resolves any of them; the viewer loads assets by `timeline.map`. Measure any map's balance with **`pnpm balance`** — an x-ray that sims a roster-symmetric mirror matchup (neutral tactics) across a seed spread and reports each map's attacker round-share, plant rate, and ending mix, flagging `ATK-SIDED`/`DEF-SIDED`/`STALLY`. Tune against the numbers, not by eye.

**Map-scale normalization is in.** `SPEED` is calibrated to Ascent, so a map whose pushes/rotations are longer in absolute image-units plays too fast for Ascent-speed defense. `mapScale(A)` derives a per-map factor from each map's characteristic distance (`charDist` = 0.6·mean(spawn→site) + 0.4·mean(mid→site)) over Ascent's, and multiplies every movement speed (`atkSpeed`, `rotSpeed`, authored-route + kill-point arrive) by it, so a push and a rotation cost the same *fraction of the round* on every map as on Ascent. Pure geometry, no per-map magic numbers — and **Ascent's scale is exactly 1.0, so seed 42 is byte-identical** (every arrive time ×1). It's threaded into `resolveRound` as a param so canonical + forks agree. This pulled the genuinely *mis-scaled* maps into balance (haven 63→57% attacker, split/lotus into band).

But **scale is not the whole story** — only Ascent is truly tuned. The residual offenders are *mis-shaped*, not mis-scaled: fracture/abyss/bind/pearl sit ~82–91% attacker with ~95% plant rate because their **sites are too far from `mid`** for the default procedural defense (which posts most bodies at mid) to contest — a placement problem `mapScale` correctly leaves alone (fracture's scale is ~1.14, near Ascent's). icebox/split lean defender-sided and sunset stalls ~37% of rounds. Fixing these is per-map anchor work (reposition `mid`/sites, measured with `pnpm balance`) — fiddly because moving `mid` also shifts `mapScale`, so eyeball tuning regresses as often as it helps. **Map rotation is live over a curated pool of the *balanced* maps**: the web store's `MAP_POOL = [ascent, breeze, haven, lotus, split]` (42–56% attacker, a healthy spread), and `fixtureMap(seed)` assigns each fixture a map deterministically from it (the other 6 stay out of rotation until tuned, like a real comp pool). The store loads a navmesh per pool map; `buildInput` sims on the fixture's map and **drops your authored plays on non-Ascent maps** (they're Ascent-coordinates — your dials still apply); the viewer loads the fixture's own png+navmesh to watch. The **editor stays Ascent** (`MAP`, where your plays live). Don't assume a non-Ascent map is balanced — the pool is the ones that are.

**N-site support is in** — the engine models N sites generally, not just A/B. `MapAnchors.sites` is `{ A; B; C? }` (the third is opt-in per map; `siteIds(a)`/`sitePt(a,s)` are the helpers), and **Haven and Lotus now field all three** (A/B/C, ~even split across them). The site dials generalize: attacker `siteBias` is a weighted pick over the fielded sites (`siteWeights`→`pickWeighted`, one rng draw), and defender `read` (`readIndex`) spans them (+1→A .. −1→last), so on a three-site map a wrong read can be **two rotations** away. The procedural defense stacks the read site, posts one watcher on **each** other site, and pushes the rest to mid. **Two-site is byte-identical**: `siteWeights`/`readIndex`/the defense split all reduce exactly to the old A/B math for `n===2` (the weighted pick over `[pA,1−pA]` is the same single `rng.chance(pA)` draw), so **seed 42 is unchanged**. Contract: `Round.site` and the `plant` event widened from `'A'|'B'` to `SiteId='A'|'B'|'C'` (additive — the viewer only displays it). The editor's `PlayEditor` renders a button per fielded site and mirror cycles through them; `Editor.vue` derives spawn+sites from `ANCHORS[MAP]` so it's correct for any map (the world is Ascent-only today, so it shows A/B). The natural next step is per-map anchor tuning so Haven/Lotus play *balanced*, not just complete.

When you touch geometry, reuse these primitives — don't write a second raycaster or a second notion of "walkable."

## Current state

Phase 0 (the keystone) works: a real deterministic engine producing full matches, the map pipeline, and a viewer rendering it on the actual Ascent minimap.

Vision is now wired end to end (roadmap step 1, done): agents have a facing and a ~120° awareness cone; `inView()` composes that cone onto the alpha-mask LOS; a duel only resolves if someone sees the other, and spotting an unaware enemy first is decisive. The viewer renders each agent's wall-clipped vision cone by raycasting the same navmesh. This is correct — keep building on it. Backstabs, off-angles, and retakes should emerge from geometry, never from hand-authored exceptions.

Utility is in (roadmap step 2): abilities fire for real and bend duels through the same geometry — no hand-authored exceptions. Controllers throw `Smoke`s (vision-blocking circles over time); initiators/attacking-duelists throw `Pulse`s (recon/flash that grant the first shot in an area-window). **Smokes are directional: an enemy smoke on the sightline blinds that viewer, never the side that threw it** (`blindedThrough()`). This is the load-bearing decision — it's what makes the `utility` attribute a net positive instead of self-harm (an earlier symmetric model made higher utility *lose* more). Reach/duration scale with the caster's `utility` (0..1), so the stat expresses through play. If you extend utility, preserve that invariant: more utility must help its owner.

The procedural execute now **reads like a coordinated hit** (the viewer is the product — Phase-0 watch quality, not just gameplay). Two changes, both for how it *looks*: (1) the pushers **fan across the site entry** (`ATK_SPREAD`) instead of all A*-ing to one stacked point — each takes a distinct lateral slot on a line perpendicular to the approach (the entry deepest+first, support eased back to lob util), so they hit from spread angles with cones fanned out, not a blob of overlapping bodies; and (2) a controller with kit to spare **double-smokes** — a second `Smoke` walls the mid↔site **connector** (`lerp(sitePt, mid, 0.5)`), blooming just after the first for sustained coverage, so a high-util controller visibly does more and the hit shows two walls up through the fight (the viewer draws both clipped to walls). **Balance is held by measurement, not luck.** The fan is the sensitive one — a *wide* fan (`ATK_SPREAD` 34) consistently crossfires the concentrated defense and swung ascent 53→61 / tipped haven+lotus+split; a **gentle** fan (18, ±27px) keeps all 5 pool maps `ok` on `pnpm balance` while still reading as a spread. The second smoke is **PLANNED, not thrown** (centre + time a deterministic function of geometry — no jitter, no `rng.range`), so it draws zero new rng and is symmetric on a mirror → the **pool balance is byte-identical to fan-only** (it's win-rate-inert, which is the point: free visual intelligence that can't warp map fairness). `jitter` draws a fixed count regardless of amount, so the fan doesn't desync setup rng either — only the resulting paths/duels diverge. Both changed the canonical stream (movement + the active second smoke perturb resolution), so seed 42 + the committed `timeline.json` were regenerated. Knobs: `ATK_SPREAD` (fan width — balance-sensitive, measure before raising), `CTRL_RESMOKE_U` (utility gate for the second smoke), `RESMOKE_T0`/`RESMOKE_R`/`RESMOKE_DUR`.

The attackers also **spawn separated across the barrier** (like real Valorant) and converge to the push — but this is **viewer-only** (`SPAWN_FAN`/`SPAWN_CONVERGE` in `viewer.ts`), *not* an engine change, and that distinction is load-bearing. Separating the spawns *in the sim* was tried three ways (perp spread, a converge-via-regroup path) and **each one re-tuned the whole pool** (breeze→DEF-SIDED, lotus→STALLY, split swinging 14pts) — the engine's balance is calibrated to attackers starting near one point, and *any* change to their spawn/route/arrival shifts per-map combat. So the engine keeps the tuned single-ish spawn, and the viewer renders the separation as a flourish: each attacker is offset laterally across a shared perpendicular at `t=0`, decaying to 0 by `SPAWN_CONVERGE` (~0.12), so they start spread and collapse onto the real engine path before any combat. Pure render — no `MatchTimeline` change, determinism + map balance **byte-identical**. The lesson generalizes: *movement that must look better but can't move balance belongs in the viewer, not the engine* (same playbook as the trap-stutter warp). The same lesson then settled the defender-blob: the procedural defense piles bodies on one point (the read-site stack at round start, then *all five* converging onto the contested site post-rotation — every defender's goal is `sitePt`). Spreading them in the engine was tried (`DEF_SPREAD`) and **broke the pool in opposite directions per map** (split→DEF-SIDED at 38.7, lotus→ATK-SIDED at 61.9, even at spacing 20) — defenders fight *from* their hold, so there's no single spread that holds balance. So the de-stack is **viewer-only too**, but as a general **per-frame separation pass** (`SEP_MIN`/`SEP_ITERS` in `viewer.ts`) rather than a precomputed offset: render computes every agent's base position (incl. the spawn fan), then runs a few relaxation iterations pushing overlapping **same-side** bodies apart to `SEP_MIN`, then applies (snapping any nudged body to a walkable cell). It's recomputed fresh each frame so there's **no drift**, it de-stacks *whatever* is piled at any moment (mid stack, site pile, an attacker bunch — it fixed the residual push-clump for free), and it's pure render → engine, `MatchTimeline`, determinism, and map balance all **byte-identical**. Why a separation pass and not the per-cluster `holdFan` I first tried: the debug showed all defenders depart at `t≈0.03` (contact fires almost immediately), so there's no sustained "hold" phase to gate an offset on — the pile is dynamic, and only a per-frame relaxation catches it. Knobs: `SEP_MIN` (spacing — 38 reads as distinct bodies), `SEP_ITERS`. Verified in headless Chromium: attackers fan across the barrier, the mid defenders read as a spread triangle, no overlapping rings anywhere.

Sentinel kits are in (the role had **no** match expression — controllers smoked, initiators/attacking-duelists pulsed, and **sentinels cast nothing**, a quarter of the roster idle). A sentinel now arms a **flank trap**: a persistent watch-zone on the off-site lane (`lerp(mid, otherPt, 0.5)`, `TRAP_R`/`TRAP_R_UTIL` reach, armed `TRAP_T0`..`+TRAP_DUR` — most of the round, not a thrown window) that grants the **sentinel's side the first shot** against any enemy crossing it. It reuses the `Pulse` first-shot machinery (side = the sentinel's) but is placed on the back door and stays armed, so the other roles fight the site while the sentinel watches the flank — and a **lurk/flank is punished by geometry, not a scripted exception**. The interplay is real: a lurk into a trapped flank drops the attacker from ~53% to ~48% round-win (lurk beats a committed defense; a sentinel trap beats a lurk — the manager reads the matchup). It's symmetric (both teams field a sentinel), so **map balance is unchanged** (the 5 pool maps stay `ok` on `pnpm balance`), and it draws rng (the trap's placement/timing), so it **changed the canonical stream** — seed 42 is now **9–13, 22 rounds / 155 kills**, the committed `timeline.json` regenerated. Tuning knobs: `TRAP_R`/`TRAP_R_UTIL` (how wide a lane it covers), `TRAP_DUR` (how long armed). The `ability: 'trap'` event is additive (the field is a free `string`).

The trap now also **SLOWS** — the first movement-affecting ability in the engine (denial, not just a reveal). Any agent whose **path** crosses an enemy trap zone (`pathHitsZone(path, c, r)` — segment-vs-circle over the authored/A*'d path) has its `arrive` delayed by `TRAP_SLOW`·`scale`, so a lurk/flank into a trapped lane **hitches and arrives out of position** (compounding the lost first-shot). It's a setup-time pure function of paths + trap geometry (no rng) applied **before the fork clones spread `arrive`**, so forks inherit it and True Odds stays byte-identical; it's `scale`-normalized so the cost is the same round-fraction on every map. This roughly **doubled the lurk-counter**: a lurk into a trapped flank now drops the attacker ~53.6%→**44.4%** (was ~5pt with reveal-only, now ~9pt). It's symmetric (both teams field a sentinel) so **the 5 pool maps stay `ok`** on `pnpm balance`, but the delayed arrivals perturb resolution, so it **changed the canonical stream** — seed 42 is now **13–12 (NCT), 25 rounds / 176 kills**, the committed `timeline.json` regenerated. Tuning knob: `TRAP_SLOW` (how hard a tripped enemy hitches).

The slow is now **surfaced visually** — a tripped agent visibly **stutters** in the viewer (and the editor preview, which is the same `Viewer`). No contract change: the viewer already had the trap geometry (the `ability` event's `at`/`r`/`side`) and each agent's `path`, so it replays the engine's `pathHitsZone` trigger (`trapEntryFrac` — first distance-fraction the path enters an enemy trap) and **warps its own motion** to pause the agent for `HITCH_DUR` at that crossing, then resume — *same total `arrive`* (the pause is stolen from the travel, not added), so nothing about timing or determinism shifts. While hitched the agent's ring pulses amber (`.ace-ag.tripped`). The cue lives on the ring, never a competing `transform` (the `<g>`'s transform is the agent's position). The math: `posWithDepart` takes an optional `Hitch{frac,dur,start,end}` and injects the pause via `easeInv(frac)` so the eased distance is exactly `frac` at the hitch; `facingOf` threads it too. Verified on the canonical sample: ~4.1 agents/round hitch on an enemy trap (both sentinels' traps, ~2/round each). Purely a render concern — the engine, the `MatchTimeline` contract, and seed 42 are untouched. Natural next: an attack-side spike-watch trap.

Utility is now **drawn on the map** (the x-ray was blind to it). The `ability` event carries optional **geometry** — `at` (centre), `r` (radius), `until` (end `t`), `side` — emitted by the engine for every smoke/pulse/trap/lineup (derived from the same `c`/`r`/`t1` the round already uses, so **no new rng draws — the score is byte-identical**, only the timeline gained data). A **smoke** is a solid grey vision-blocker, a **flash/recon** a bright burst that fades over its window, a **trap** a side-tinted dashed watch-ring (an armed sensor). So watching a match back you now see the smokes wall off sightlines, the flashes pop, and the sentinel traps watching the flanks — the tactical picture is legible. The fields are optional + additive so a consumer that ignores them is unchanged and `version` stays **1** (an old timeline without `at` is simply skipped). The committed `timeline.json` was regenerated to carry the geometry.

Team chemistry is in (the counterweight to the transfer market). Each player carries a `tenure` (seasons of shared play with their CURRENT club, on `Player`, additive/optional). The engine derives a per-team **cohesion edge** from the fielded five's mean tenure (`teamChem` → `CHEM_EDGE`·min(1, mean/`CHEM_CAP`)) and adds it to every duel for that side — so a settled core out-duels an equal-talent **brand-new roster** ~60% (calibrated: a constant per-duel edge compounds hard over a match, so `CHEM_EDGE` is only **1.0**). A fresh signing has tenure 0 (hasn't gelled) and drags team cohesion down until it builds; `CHEM_CAP`=1.5 seasons to fully gel. **No tenure data (undefined — the engine sample) → 0 edge**, so seed 42 is byte-identical (it's a pure function of the roster, applied differentially, so equal-chemistry teams cancel too). The world owns tenure: `makeClub` starts an established roster gelled (tenure 2 > CHEM_CAP), `makePlayer` defaults a new player to 0, the store's `retag` resets a signing to 0, and tenure grows ~+1/season (your five in-season, AI off-season). This makes **roster stability a real asset** — you can't buy five stars and instantly be a top team, and it rewards the homegrown/dynasty path. The squad screen shows team **cohesion %** + a `gelling N%` tag on fresh signings. Bounded/fair (DESIGN §2/§18). It's a per-player/per-team duel edge like form/compEdge — no `MatchTimeline` contract change.

Match-night form is in (the match-expression layer of the three-layer model). Each player draws one form edge per match (`FORM_SWING`, in `simulateMatch` so it's held all match), added to their duel edge — same roster, different night. Drawn in a fixed team/player order to stay deterministic; if you add draws before it, the whole stream shifts (that's fine, just regenerate the sample). Keep it bounded and *fair* (DESIGN §2/§18: a bust is a risk you took, never the dice mugging you). The viewer shows it live via the scoreboard (K/D tallied from kill events — no contract change). The third layer's missing piece, *potential behind fog*, belongs to scouting/management (Phase 3), not the engine.

True Odds is in — the determinism thesis turned into a feature. The round resolution is now a pure function, `resolveRound(agents, smokes, pulses, nav, …, rng)`, split out from setup. `simulateRound` runs it once canonically on the **match rng**, then `FORKS` (120) more times on *throwaway* agent copies seeded by `forkSeed(seed, n, i)` to measure how often the attacker wins — the round's `winPct`. **The forks must never draw from the match rng** (that's why they get their own `new Rng`); this is what keeps the canonical timeline byte-identical. `winPct` is additive on `Round` (version stays `1`); the viewer plots it. If you change setup-time rng draw order, regenerate the sample.

Tactics is in — the manager's lever, and the bridge to the management game. `MatchInput.tactics?: [Tactics, Tactics]` (the type lives in `@ace/shared/models`). The round *resolves* it: attacker `siteBias` weights site choice; `tempo` scales attacker arrival + execute timing; defender `read` decides where bodies pre-commit (they set up on the read, **not** the actual site, so a wrong read is paid for in rotation time — rotators move at 0.6 speed and arrive late); `aggression` pushes mids forward and trades the held-angle `holdBonus` for early picks. The attacker-site-vs-defender-read mind-game is real (~7pt round swing on identical rosters; verify by holding rosters equal and flipping only the read). **Every team always has tactics**: owners author their own; a club/bot without them falls back to `DEFAULT_TACTICS` (in `@ace/shared`, so the engine and the future management layer share one default). Tactics is an engine *input* — it does not touch the `MatchTimeline` contract or the viewer.

Per-player attack roles are in (the seed of the tactics editor). `Tactics.attack.entry` (player id) leads the push — arrives 15% sooner, takes opening contact; defaults to `bestEntry` (highest entry attr) if unset. `Tactics.attack.lurk` (player id, opt-in) peels one player off the execute to a flank hold (`lurkPt = lerp(mid, otherSite, 0.4)`, facing the rotation), trading a softer 4-player hit for flank picks + a late man-advantage. The lurk is a deliberate **tradeoff** (~even win rate, ~0.3 flank kills/round) — tune `lurkPt`/arrival if you want it stronger, but keep it a choice, not a free win. Elevation decision: **stay 2D** — walls are already enforced by the alpha mask; a per-map height layer is deferred until a genuinely vertical map needs it.

Authored plays + kill points are in (the engine half of the cs-manager-style editor). `Tactics.defense.play?: Play` (in `@ace/shared/models`) lets an owner place defenders **exactly** instead of leaving them to the procedural read: `Play.plans` is one `PlayerPlan` per player — a `pos` to hold, plus an optional **kill point** `rotate: { pos, onDeathOf }` that re-routes that player when a named teammate dies. The engine resolves it in two places: setup branches on `defTac.defense.play` (authored agents spawn at `plan.pos`, `anchor: true`, with `rotatePlan` resolved from the trigger player id → handle via `byId`; a planless player falls back to holding the site); and the kill-resolution loop in `resolveRound` fires the trigger — when `loser.handle` matches a live agent's `rotatePlan.onDeathOf`, it re-paths that agent (`pathfind` → `rotate.pos`, `departT = t`, `arrive = arriveTime(path, ROTATE_SPEED)`, then clears `rotatePlan`). This **reuses the `departT` hold-then-move machinery** info-gated rotations already gave us — a kill point is just a hold whose release trigger is a teammate's death instead of contact, so it costs no new viewer contract (still `version: 1`, the rotation rides the existing `move` event). The fork clones preserve `rotatePlan` (spread, and forks run before the canonical pass) and reset `exposedUntil`/life, so True Odds stays byte-identical and the authored play stays dormant when unset (seed 42 unchanged). It's a **reactive** play: lose the bait and the team collapses onto the kill point, so a wrong trade is punished by geometry, not a scripted exception. v1 is hold + one conditional rotation; the natural extensions are more triggers (`onContact`, at-time), attack-side plays, and N-step chains.

Routes are in (the path, not just the endpoint — works for both sides). `PlayerPlan.route?: Vec2[]` is the ordered waypoints walked **into** the hold: `[...route, pos]` is the full path the engine builds, so an empty/absent route means "start already on the hold" (the original byte-identical behaviour). An authored defender with a route departs at 0 and walks it at normal speed (`arrive = arriveTime(path)`), so a **longer route is a real tradeoff — the player is set up later**. This needed no new viewer contract and no new playback code: `posAt`/`facingAt` (engine) and `posWithDepart`/`facingOf` (viewer) already operate on the `path` array, so a multi-waypoint route just rides the existing `move` event (still `version: 1`). The fork clones share the `path` ref but only ever reassign it (never mutate), so True Odds stays byte-identical and routes stay dormant when unset (seed 42 unchanged). The browser editor draws them: pick a player, click the map to drop waypoints (spawn→hold, in order), drag to move, click to remove — every edit re-sims live. The editor also reads the navmesh for **walkability feedback**: a hold/waypoint on a wall gets a red ring and a verbatim route segment that clips a wall is drawn red (an *un*-routed kill-point rotation is A*'d by the engine, so its straight intent-line is deliberately *not* flagged — only authored verbatim paths get the wall check). **Kill points are routable too**: `rotate.route?: Vec2[]` authors the rotation's path — when the trigger fires the engine walks `[here, ...rotate.route, rotate.pos]` verbatim, else it falls back to `pathfind` (so an unrouted kill-point stays byte-identical). The fork clones spread `rotatePlan` (route included, by ref, only ever reassigned) so True Odds is unaffected. **Routes are capped** at `MAX_ROUTE_WAYPOINTS` (5, in `@ace/shared`) — a play is a *sketch*, not turn-by-turn micro; the editor enforces it (each of a player's hold route and kill-point route gets its own budget) and the engine stays agnostic to length.

Authored facing + kill-point triggers are in (the "quick wins" pass). `PlayerPlan.face?: Vec2` is a point the defender watches from the hold — the engine sets `holdDir = face ? unit(pos, face) : unit(pos, atkSpawn)` (default unchanged), so authoring an angle is a real off-angle/crossfire lever and rides the existing `move.hold` (no contract change; the viewer already renders facing). And the kill point's release is now a tagged trigger, `rotate.trigger: RotateTrigger = {kind:'death',player} | {kind:'contact'} | {kind:'time',t}`: **death** is the classic bait (fires in the kill loop when that handle dies), **contact** fires when `contactT` is set (first kill or an attacker reaching the site — reuses the info-gate signal), **time** fires when the round clock passes `t`. The last one *is* the timing lever — a hold at mid with a `time` trigger to the site is a staggered "hold then fall" default, no new machinery. All three are resolved by one `fireRotation` closure (walk the authored route verbatim, else A*), so contact/time triggers reuse the exact `departT` hold-then-move path the death trigger and info-gated rotations already share. Forks spread `rotatePlan` (trigger by ref, only reassigned), and every field is opt-in, so True Odds and seed 42 stay byte-identical. The editor exposes facing as a draggable nub per defender and the trigger as a kind-picker (+ a teammate select for death, a time slider for time). Next on the same primitives: N-step chains and attack-side plays.

Attack-side plays are in — the other half of the editor, where routes + triggers + lineups converge into an authored execute. `Tactics.attack.play?: Play` mirrors the defense play: per-player `pos`/`route`/`face`, a push `rotate` (a lurk that flanks on a death/contact/time trigger), and attack `lineups`. Three attack-specific bits: (1) `Play.site?: 'A'|'B'` **forces the round site** — `site = atkTac.attack.play?.site ?? (rng roll)`, so the rng draw only happens when unforced and the no-play sample stays byte-identical; (2) authored attackers spawn at a **deterministic per-index spread** off `atkSpawn` (no rng) and are A*'d to their spot when unrouted, walked verbatim when routed (same rule as defenders, but defenders start *on* the hold while attackers travel from spawn); (3) the default facing is **forward** (`unit(spawn, pos)`) not toward-spawn. The trigger resolution (`resolveTrig`) and the lineup builder were generalized to both sides — lineups now carry their `side` (attack smokes blind defenders, defense smokes blind attackers; `blindedThrough` holds), and a caster on either side skips their procedural auto-cast. Every field is opt-in (NCT/MRD ship no `attack.play`), so seed 42 is byte-identical. The editor authors it through the **same `PlayEditor`** (a `mode` prop flips the facing default + adds an A/B site picker); each team now has an `attack` and a `defense` play button. Verified: an A-execute forces site A:12/B:0 and moves the score; forcing B with A-positioned players tanks it (positions must match the site — the owner's call, like a hold in a wall).

Utility lineups are in (the manager authors the util, not just the positions). `Play.lineups?: Lineup[]` — each is `{ player, kind: 'smoke'|'flash'|'recon', at: Vec2, t }` — feeds the **same** `smokes[]`/`pulses[]` geometry the procedural utility builds, so an authored smoke blinds attackers through it (the `blindedThrough` side invariant holds: defensive `side`, blinds the enemy) and a flash/recon grants the defender the first shot in its window. Reach/duration still scale with the caster's `utility` stat (`SMOKE_R + SMOKE_R_UTIL*u`, etc.), so the stat stays meaningful. **A lineup replaces that caster's automatic cast** — `authoredCasters` is collected first and skipped in the procedural loop, so you don't get double utility from one player; players you don't author keep their auto-cast. Lineups draw **no rng** (the point and `t` are authored, reach is a pure function of the stat), so they don't perturb the rng stream — forks and canonical use the one array built before the fork loop, and seed 42 stays byte-identical (no play → no lineups). They ride the existing `ability` event (no contract change; the event has no position, so the *match viewer* doesn't draw the cloud — but the **editor** does, since it owns the `Lineup` data: a draggable center + a translucent reach circle whose radius mirrors the engine, plus a caster select and a time slider). v1 is defensive (lives on `Tactics.defense.play`); attack-side lineups come with attack-side plays.

Trading is in (round dynamics 1 of 3). `duel` now takes a numeric `surprise` edge (not `-1|0|1`); resolveRound composes it from vision (`±FIRST_SHOT`), pulses (`±FIRST_SHOT`), then a **trade**: a kill sets `winnerAg.exposedUntil = t + TRADE_WINDOW`, and a teammate who can see that exposed killer gets `±TRADE_EDGE` (via `Math.max/min`, so it flips a held first-shot but never weakens a bigger same-side edge). `exposedUntil` must reset to `-1` in the fork clones (it does) or odds drift. Trading favours the grouped side (~+13pt to attackers), and ~37% of kills get traded. Viewer tags trades in the kill feed (⇄) — derived from the event stream, no contract change.

Modeled retake is in (round dynamics 3 of 3). Post-plant, a defender within `DEFUSE_R` of the spike (`plantPos`, captured at plant) with no attacker within `SITE_R` channels a **defuse**; `DEFUSE_TIME` of uncontested time wins it and finally emits the long-dormant `defuse` event (the viewer renders it). Crucially the hold edge **inverts** post-plant: `duel` now takes an explicit `holdEdge` (not `def.holdBonus` internally) and resolveRound passes `planted ? -POSTPLANT_HOLD : d.holdBonus` — so attackers hold the crossfire after the plant, defenders push in. That inversion (POSTPLANT_HOLD=10) is what rebalanced the retake (which alone over-helped defense to ~41%) back to **~49% attacker, ~6% stalls** with all three dynamics in. Note `SPIKE_TIME` doesn't bind (rounds resolve before detonation) so it's not a balance lever — `POSTPLANT_HOLD` is. With trading + info-gating + retake all in, the canonical sample was regenerated again.

Info-gated rotations are in (round dynamics 2 of 3) — the defensive counterplay to trading. Agents gained `departT` (when they start moving; `Infinity` = holding for info). Anchors and attackers depart at 0; **rotators hold their read** (`departT = Infinity`, watching their lane from `st.from`) until **contact** — the first kill (`hadKill`) or any attacker within `SITE_R` of the site — then `departT` is set to that `t` and they rotate at `ROTATE_SPEED` (0.85, faster than the old 0.6 since they now move with purpose). `posAt`/`facingAt` hold at `path[0]` until `departT`. This rebalanced trading back to ~47% attacker and cut stalls (time%) from ~11% to ~7%, so `HOLD_BONUS` went back to its original 6 (the 9 was a temporary patch). **Contract: the `move` event gained `departT`** (additive, version stays 1); the viewer mirrors the hold-then-rotate via `posWithDepart`. Note: the hoped-for "fast hit punishes a wrong read harder" interplay came out ~tempo-flat (rotation delay scales with contact either way) — parked as future tuning; the read itself is still a strong lever. Tuning knobs: `TRADE_WINDOW`, `TRADE_EDGE`, `ROTATE_SPEED`, `HOLD_BONUS`.

The IGL trait is in (the parked "adaptive mid-round reads", now a player-model lever). `iglRotateMul(team)` returns a rotation-speed multiplier for the **defense's procedural rotators** (the info-held bodies), scaled by the in-game leader's cerebral stats — `(igl.gameSense + igl.clutch)/2`, mapped to **~0.85..1.20** centered at 70 (no IGL = neutral 1.0). It multiplies `ROTATE_SPEED` only for the rotators' setup-time `arrive` (`rotSpeed = ROTATE_SPEED * iglRotateMul(defTeam)`), so a sharp caller gets out-of-position bodies onto the real site faster on contact. The elegant part: only rotators move (anchors are already on site), so the edge **scales with how wrong the read was** — it reads as adaptive recovery, not a flat buff. Bounded and *fair* (DESIGN §2/§18): a wrong pre-round read is **mitigated** by a great IGL, never erased, and a weak caller is a roster gap you fix by fielding a better leader. An elite IGL (92) beats an otherwise-identical weak one (50) ~75% of matches (that figure also rides the IGL's own gameSense/clutch in duels — the rotation effect is the smaller, cleaner part). It draws **no rng** (a pure function of the stat) and lives entirely in setup `arrive`, so the fork clones inherit it by spread and True Odds is unperturbed; the contract is untouched (no viewer change — the IGL badge already shows on the scoreboard). It's engine behaviour, not a manager input, so it changed the canonical stream: the committed sample was regenerated (seed 42 is **13–5, 18 rounds / 120 kills**, one former stall now a defuse). Natural extensions: an attack-side IGL (execute coordination), and letting the IGL also shave the contact-reaction delay (anticipation), which would need threading the factor into `resolveRound`.

Comp is in — the other half of "what you field." `MatchInput.comp?: [Comp, Comp]` maps player id → agent; a player not listed falls back to their **top-mastery agent** (`topAgent`), so every team always has a comp. Per match, `addLoadouts` builds a `Loadout` per player: the fielded agent's **role** (via `AGENT_ROLES`) decides the kit fired in the utility loop (so comp reshapes a team's whole utility profile), a `compEdge` (~±5, from the agent's patch `tier` and the player's `mastery`) adds to the duel, and `utilFactor` scales their utility by mastery. Loadouts are built once per match and threaded into `simulateRound` like `form`. Fielding mastered meta mains beats off-pool picks ~88% of matches (identical rosters). The fielded agent is surfaced additively on `PlayerMeta.agent` (version stays `1`); the viewer shows it on the scoreboard. **Engine assumption: player `handle` is unique within a match** — kill events, `form`, and `loadouts` are all keyed by handle. Real orgs have distinct handles; if you ever synthesize teams, give them unique handles or these maps collide.

Economy is in — a real buy rhythm (`economy.ts`). `decideBuy(creds, opp, lossStreak)` reads our bank, the enemy's, and our streak; the key behaviour is **saving** (eco to bank a real buy rather than half-buy into rifles). `nextCreds` now **spends the buy** (`COST` per tier) then earns (win 3000 / loss bonus 1900·2400·2900 / +200 a kill / +300 for a plant), clamped 0..9000 — so buys actually drain and a buy-and-lose streak bleeds you toward an eco. Buys feed weapon `TIER`, so an eco is a weaker round (shows up as a low `winPct`). It's engine-internal (not a manager input — in-game money is an in-game call); no contract change. The viewer shows each team's buy on the scoreboard. Tactics, comp, and economy all changed the canonical stream; the committed sample was regenerated (seed 42 is now 23 rounds / 164 kills).

To keep it browser-bundleable: `packages/maps/src/index.ts` is a **pure barrel** (geometry only); the node-only `loadNavmesh` lives in `load.ts` and is imported **directly** (`cli.ts` does a relative `../../maps/src/load.js` import) so it never reaches the web bundle. The committed `timeline.json` is still the CLI artifact but the viewer no longer needs it (it sims live).

## The world layer (`@ace/world`) — Phase 1 begins

`@ace/world` is the persistent-world core: it generates a league and resolves a season, and it is **pure and deterministic exactly like the engine** (same `Rng` from `@ace/engine`, the navmesh injected, no `Date`/`Math.random`/I/O). A whole season is a function of one seed. This is deliberate: the **single-player loop runs it client-side now, and the Phase-2 server worker will run the same code** to resolve scheduled ticks — no fork, no rewrite.

- `clubs.ts` — `makeLeague(seed, n)` → `Club[]` (`{ team, tactics, strength }`). Rosters are role-shaped (`ROLE_SHAPE` biases each role's attributes so identity is legible in the stat line), handles are drawn **without replacement** from a global pool (the engine assumes unique handles within a match — keep them globally unique so cross-club matches never collide), and strength descends across the field with noise (a hierarchy, not a fixed ladder). `makeTactics` varies the dials around sane ranges so AI orgs feel distinct.
- `schedule.ts` — `roundRobin(n)` / `doubleRoundRobin(n)` via the circle method (n even). A season is `Matchday[]`, each a set of `{home, away}` club-index fixtures.
- `divisions.ts` — the **rank pyramid** (DESIGN §17). The world is `DIVS` tiers of `DIV_SIZE` clubs — the pro leagues up top (`Premier`, `Challengers`) then the solo-queue ladder (`Radiant`…`Iron`), 11×10 = 110 total (the store owns `DIV_NAMES`/`DIV_SIZE`/`PROMO`/`START_TIER`). `membersOf(division, d)` lists a tier's club indices; `divisionSchedule(members)` builds that tier's double round-robin (the circle method over `0..m-1`, mapped to real club indices); `promoteRelegate(division, tables, k)` swaps the bottom `k` of each higher tier for the top `k` below at season's end, returning the new `division` map + the `DivMove[]` for a banner. Pure — `division` is store state (a club-index → tier map), so the engine, the `Club` type, and seed 42 are untouched. **Resolution is split by relevance: only YOUR tier full-sims** (5 fixtures/match-day, watchable); every other tier is `quickResult` (a deterministic strength-vs-strength scoreline, no engine call), so a 110-club world still sims a season in seconds. You start mid-table in Gold (`START_TIER`) and climb; promotion/relegation runs across all 11 boundaries in `advanceSeason`, income scales by tier (`divMult`), and the transfer board is scoped to clubs within a tier of you (`marketEligible`).
- **Procedural name generation** (`clubs.ts` `genClubIdentities`/`genHandles`, parts in `names.ts`) makes the world *any* size: curated pools first, then procedural overflow — adjective×noun club names (the full combo space shuffled, so a tier isn't all "Mavericks") with a de-duplicated 3-letter tag, and coined syllable-combo handles (`VEX`+`AR`→`VEXAR`) before any numeric fallback. A 110-club / 550-player world generates with zero handle/tag/name/id collisions and a disjoint free-agent pool. This is also the unlock for a Phase-2 server world of thousands.
- `resolve.ts` — the **shared resolution core** (Phase-2 prerequisite, `docs/PHASE2.md` §2). Pure functions the single-player store calls today and the server tick worker will call unchanged: `buildMatchInput` (fixture → `MatchInput`), `quickResult` (a no-engine strength-vs-strength scoreline for dormant divisions), `resolveWorldDay` (a whole match-day across divisions — owns the `day, slot+division·1000` seed convention, with `sim`/`quick` and the `full(d)` predicate **injected** so the caller supplies the navmesh + any overlay), and `settleClub`/`divMult`/`squadWageBill` (tier-scaled season settlement). No Vue, no I/O — this is the exact boundary both runtimes share, so the store became a thin reactive wrapper. Seed 42 + the season CLI are untouched (engine unchanged); the only behavioural delta is AI club settlement now rounds sponsor/prize separately (a ≤$1 consistency fix, and the world is regenerated per playthrough anyway).
- `state.ts` — **`WorldState`**, the whole persistent world as ONE value object (Phase-2 spine, `docs/PHASE2.md`): `seed`, `season`, `day`, `patch`, `clubs: WorldClub[]` (each a full `roster` + plan + tier/group + balance + `owner` overlay), `results`. `createWorld(seed, {tiers, size, promo})` generates it (strength-descending field split into tiers); `simulateSeason` resolves a season headless (every division `quickResult`-ed); `advanceWorld` rolls the off-season (top-tier playoffs → `settleClub` → `developPlayer` → `patchMeta` → `promoteRelegate`) and returns the new world + events. `startingFive`/`clubTeam` derive the fielded five from a roster. Pure and headless — **`pnpm world --seed 7 --seasons 14`** runs it with no Vue/DB/navmesh and shows the ladder churn (clubs climb/fall, dynasties form, the meta shifts), deterministically. This is the exact code the Phase-2 server tick worker runs; the single-player store will consolidate onto this shape (clubs carrying depth + plan uniformly) next. Doesn't touch the engine or seed 42.
- `season.ts` — `resolveFixture` runs `simulateMatch` (no stored timeline; a fixture's `seed = fixtureSeed(seasonSeed, day, slot)` is stable, so the web app **re-sims to watch**). `standings()` builds the table (points → round diff → rounds for).
- `playoffs.ts` — the **season climax** (DESIGN §17 "an ending worth chasing"). The regular-season table seeds a top-4 single-elim bracket (`runPlayoffs(standings, seasonSeed, season, pool, affinityOf, resolve)` → 1v4 / 2v3 **Bo3** semis → **Bo5** final). Each series opens with a real **map veto** (`vetoMaps`): each club bans its weak maps and picks its comfort ones from the pool (ban·ban·pick·pick·decider on a 5-map Bo3; pick·pick·pick·pick·decider on a Bo5), driven by `affinity.ts#mapAffinity(teamId, map)` — a deterministic hash giving each club a comfort profile, which the store also applies as a small attr bump so the picked map *matters* (a team plays a touch better where it's comfortable). The veto-decided maps are played in order; the resolver takes the map: `resolve(home, away, seed, map)`. `Series` carries `maps`/`veto`/`need` for the UI (the bracket shows the ban/pick strip + per-game map; watching a playoff game forces its veto map, not the seed-derived one). Pure/deterministic — match resolution is **injected**, every game seed is a stable hash (`playoffGameSeed`), re-simmable to **watch**. `finishOf` drives `playoffPrize` + a title tally. Doesn't touch the engine or the season CLI, so **seed 42 is byte-identical**.
- Verify with `pnpm season -- --seed 7 --clubs 8`: deterministic across runs, and the `strength→rank agreement` line should sit high but not perfect (healthy upsets). If you add rng draws to club/season generation, the whole world shifts — that's fine, just expected.
- `develop.ts` — the **development model** (Phase 1's player-model spine), now **continuous**: ability moves toward each player's hidden per-attribute **potential** (generated in `makeClub`, fogged by scouting) along the esports aging curve (DESIGN §4.4): teens close ~⅓ of the gap-to-potential a year, the early-20s peak, then decline past peak — **mechanical** attrs (aim/movement/entry) fade earlier/faster than **cerebral** ones (gameSense/utility/clutch), the veteran-IQ effect. **Development happens in-season, match by match** (`developInSeason(p, played, games, rng)`), not just at the off-season: a starter gets **reps** → grows; a benched player grows far less and **rusts** (loses mechanical sharpness) — so playing a prospect develops him and benching him regresses him. The annual curve is split `SEASON_SHARE` (0.6) in-season + the rest as the off-season **bootcamp** (`developPlayer(p, rng, frac)`), so a full-time starter's yearly pace is **conserved** while playing time becomes a real lever. **Ability is now fractional** (a season of <1-point daily steps would otherwise round to nothing); the UI rounds for display, and `overall`/`squadRating` already round. Shared `curveStep` keeps the two ticks from drifting. **Potential is a narrowing cloud** (DESIGN §4), not a fixed point: a player carries `potVar` (plasticity, high for teens, ~0 once settled — generated in `makePlayer`), and each development slice `resolveCeiling` drifts the ceiling **up if played, down if benched/idle** (a shared luck draw so a prospect booms or busts coherently) then narrows `potVar` toward 0, where it **locks**. Bounded (plasticity shrinks geometrically) and fair (a bust is a bet you took) — so playing a gem realises his upside (ceiling can climb to 97), benching him busts him (collapses to ~78), and the gamble lives only in youth (`potVar≈0` veterans are untouched). Pure/deterministic (one `Rng`, fixed order). The roster screen shows live per-attribute ▲/▼ deltas vs a season-start baseline (`snapRosters`). The **match engine ignores `potential`, so seed 42 is byte-identical**. Each player also has a **solo-queue rank** (`soloRank(overall)` → Iron…Radiant, 8-point bands with sub-tiers) — their individual skill on the VALORANT ladder, a *different axis* from their club's division, so a Radiant player on a Gold club reads as a gem; the roster + market show it as a coloured rank badge. **Retirement closes the age-curve loop** (`RETIRE_HARD_AGE`=38, `retireChance(p)`, `shouldRetire(p, rng)` — a single rng draw): zero chance under 28, climbing each year (~14% at 30, ~42% at 34, forced at 38), a faded vet sooner — bounded and *fair* (a curve, not a cliff, DESIGN §2/§18). The store's `processRetirements` runs it league-wide each off-season (after aging): AI clubs reload (homegrown/journeyman by infra), **your** retirees leave `myRoster` too (so your academy pipeline is load-bearing) — you're notified via a banner, and if a retirement drops a role below the valid five, your best academy prospect is auto-graduated (or a youth called up) so you're never short. This stabilizes the world's age distribution (avg ~25 vs an un-retired ~35) at ~10 retirements/yr per 30 clubs, every club always reloading to exactly five. Pure/deterministic; the match engine never sees it, so seed 42 is byte-identical. **Team lifecycle stages + rebuild strategy are in** (DESIGN §17): `clubPhase(team)` is an **emergent** stage — `rebuilding`/`rising`/`prime`/`aging` — derived from the roster's mean age (the smooth lifecycle signal) and room-to-grow (current vs potential), so a club *moves through* the arc as its core develops and ages (it isn't assigned). The store reads it: an **aging** AI club doesn't wait for the retirement cliff — `manageAiClubArcs` has a well-run one proactively shed its oldest for youth a year early (a managed transition — a dynasty that *reloads* — verified to cap a dynasty's worst single-season strength drop at ~6, not a collapse), so the league keeps a spread of teams at different stages instead of synchronized booms and busts. The load-bearing piece for a *stable* spread is **persistent club character**: `clubAgeChar(id)` (a deterministic id hash, −3..+3) biases a club's roster ages at generation **and** the ages of players it reloads, so some orgs always run a veteran core (cycling prime→aging→rebuild) and some a young one (perpetually rising) — keeping the league's ages spread (~20–30) so the stages hold a healthy mix (~1/39/44/16% RBLD/RISE/PRIME/AGE) season over season rather than pulsing as one. The standings show each club's stage as a colour chip next to the HQ meter (read the league: which dynasties are aging/vulnerable, which young teams are rising). `makePlayer` gained an opt-in `ageShift` (the club's age character; 0 byte-identical). Engine untouched, so seed 42 is byte-identical; the world/season CLIs stay deterministic (the gen stream shifted once when `clubAgeChar` replaced a random age draw — expected, the world regenerates per playthrough).
- `facilities.ts` + the web store — the **HQ** (DESIGN §8), the money sink that compounds development. Three upgradeable rooms (`FACILITIES`, levels 0..`FACILITY_MAX`=5, cost `6000 + level·7000`): **Bootcamp** speeds growth-to-potential, **Recovery Center** slows the age decline, **Analyst Room** biases the ceiling cloud up and cuts bench rust. `facilityBoost(f)` reduces the rooms to a `DevBoost { growth, decline, ceiling, rust }` that threads through `develop.ts`: `curveStep`/`resolveCeiling`/`developInSeason`/`developPlayer` all take a `boost` param defaulting to **`NO_BOOST`** (×1 / +0), so AI clubs, the `world`/`season` CLIs, and every existing call develop **exactly as before** — only your boosted roster differs. Crucially the boost scales the *post-draw* values, never the rng calls (same number of draws, same ranges), so the development stream's shape is unchanged and **seed 42 stays byte-identical** (the match engine ignores all of it anyway). The store owns the `facilities` ref, charges `balance` on `upgradeFacility`, and applies the boost to **`myRoster` only** in both ticks (in-season `developInSeason` each match-day + off-season `developPlayer` bootcamp share); it's persisted in the snapshot (old saves default to `defaultFacilities()`). A maxed HQ is a multi-season investment competing with the transfer market — verified to add ~+6 OVR to a played prospect over 3 seasons vs no HQ. The `Facilities.vue` panel (an HQ tab) renders each room with level pips, live effect text, and a scaling upgrade cost. **The rival side of the youth/HQ axis is in** (`facilities.ts` `clubInfra`/`infraBoost` + the store's `reloadAiYouth`): an AI club's **infrastructure** is a single level `clubInfra(strength)` (0..`INFRA_MAX`, a pure function — bigger orgs run better facilities), mapped to a `DevBoost` by `infraBoost(level)` (`level 0` is exactly `NO_BOOST`). `developLeague` gained an optional `boostOf(i)` (omitted → `NO_BOOST` for all, **byte-identical** since the boost scales post-draw values only), and the store passes each AI club its `infraBoost` — so well-run clubs **out-develop and retain talent**, and the gap compounds into **dynasties** (verified: top clubs ~+5 OVR over 12 seasons, spread widening modestly without runaway). Reloading is driven by **retirement** (see `develop.ts` below): when a vet hangs it up, the store's `processRetirements` refills the slot — a high-infra club graduates a **homegrown teenager** (age 17–19, infra-scaled), a weak one scrapes a journeyman — so a strong academy churns vets → prospects → stars while a weak one stagnates (verified: top clubs stay young + strong, low-infra rosters age toward the cap). The standings surface each club's infrastructure as an **HQ pip meter** (your own real facility+academy investment for your row, the strength-derived rating for AI orgs) — a scannable read on which rivals are long-term threats. Engine untouched, so seed 42 stays byte-identical.
- `academy.ts` + the web store — the **Academy** (DESIGN §8), the homegrown youth pipeline (the system only ACE can do well — it manufactures the foggiest gambles in the game). An upgradeable HQ wing (`ACADEMY_MAX`=5, cost `9000 + level·9000`) that each season delivers an **intake** of teenage prospects (`academyIntake(seed, season, level, exclude)` → `intakeSize(level)` players, age 14–18, drawn on its **own Rng** so it never perturbs the world stream) into your reserves: raw (low current ability) but a **wide ceiling cloud** (high `potVar`) — you draft blind, and the only way to resolve the cloud is reps. The load-bearing engine touch is the **academy reps path**: `develop.ts`'s `developInSeason` took a `played: boolean`, now a `DevContext = 'starter'|'academy'|'bench'` (a boolean still maps to starter/bench, so **every existing caller is byte-identical**). An `'academy'` prospect grows on a reduced rep multiplier (`REP_MUL` 0.75) with the ceiling drifting **up** and **no rust** — the academy circuit gives real reps without senior minutes, so a benched senior rots (−OVR, ceiling collapses) while an academy kid develops (verified: +6 OVR / ceiling realised to 81 over 3 seasons, vs −4 / collapse on the bench, vs +7 as a senior starter — so promoting a ready prospect into tougher competition is marginally better, the incentive to graduate). `makePlayer` gained an opt-in `ageOverride` (the role age-draw is skipped when set; existing calls byte-identical). Prospects draw a **cheap wage** (`academyWage` = 35% of a senior's, in the season settle) and **graduate** with `promoteProspect(id)` (retagged to your club, **no transfer fee** — a hit is worth many times his wage) or are **cut** (`releaseProspect`). The store owns the `academy` ref (`{ level, prospects, lastIntake }`), runs the intake once per season (`runIntake` — auto on season roll + on first build, guarded by `lastIntake`), develops prospects each match-day on a **separate Rng** (so the senior-roster stream stays byte-identical), and persists it (old saves default to `defaultAcademy()`). `Academy.vue` is a new HQ tab: the upgradeable wing + a prospect board (scouted ceiling band `owned=true`, solo-queue rank badge, promote/cut). The match engine never sees any of it, so **seed 42 is byte-identical**.
- `market.ts` — the **transfer market** (what gives money a purpose). `playerValue` prices a player: ability is the floor, *unrealised* potential in a young player is a premium, age past peak is a discount — so a 19-year-old ceiling is the dearest thing on the board and an ageing star is cheap to buy / dear to keep. `freeAgents(seed, exclude, count)` is a deterministic per-(seed,season) pool with handles disjoint from the league (the engine assumes unique handles in a match). The per-player generator was factored out of `makeClub` into **`makePlayer`** (used by both, so a signing is the same kind of object as a homegrown player) — the extraction preserved the rng draw order, so the generated world is unchanged. Signing is a **swap**: the web store replaces your same-role player, charges the net value difference, releases the old player to the pool, and remaps tactical id references so your authored plays stay coherent.
- `transfers.ts` + the web store — the **always-open market over a flexible roster**. Your club carries a **full roster (`myRoster`, ≥5)**; the matchday five is *derived* (`startingFive` = best per comp slot, one IGL), so depth never reaches the engine (it still gets exactly 5). **Buying a player ADDS them to the roster — nobody is dropped** — at the full cash price; a club you buy from banks the fee and `backfillFor`-restocks from free agency. **Selling** releases a player for their value but is blocked when it would leave the comp short of a role (the "valid five" floor). Reserves develop and draw wages like anyone (depth costs money). AI clubs stay at five and restock from free agency when they lose a player. Every move funnels through the store; `resolveListings()` runs each match-day so a listed player can sell mid-season. The whole resolution is the shape the Phase-2 server worker will run on real bids. AI transfer behaviour is **lifecycle-aware** (driven by `clubPhase`): `aiListings` has an **aging** club cash out its oldest **veteran** (a proven, age-discounted player — a rebuild raid for you to pick up cheap), while prime/rising clubs just trim their least-valuable fringe. AI clubs **value potential, not just current ability** (`aiRating` = `overall + aiUpsideWeight(phase)·upside`): a **rebuilding** club weights upside heavily (0.6), a **rising** one moderately (0.4), a **prime** one lightly (0.15), an **aging** one not at all — so `aiWantsToBuy` has a rebuilding/rising club take a high-ceiling **prospect** even at a small current downgrade (bounded by `RAW_FLOOR`=8 so it never fields someone too raw to compete), which is what gives your flipped gems real buyers. A prime club still wants a clear rating upgrade; an aging one sits out (it reloads through youth). `topRivalBid` rides the same gate, so rising clubs **bid above consensus** for upside (verified: a 74-OVR/90-pot prospect drew an extra buyer and a $31k bid on a $25k-value player). So the board reflects who's reloading and who's holding — and the prospect market is real. **Bidding wars are in** (price discovery, not a fixed price): `topRivalBid(clubs, balances, exclude, player, patch?)` is the strongest rival ceiling — every AI club that wants the player (`aiWantsToBuy`) values him at `playerValue` scaled by **eagerness** (a rising/rebuilding club pays a ~25% premium, prime ~5%), capped at 60% of its bank. The store's `bidFor(entry, amount)` resolves a bid: you sign at your offer only if it clears the seller's asking price **and** beats that rival ceiling, else it returns the leading club + bid so you can raise or walk (the war). A contested player (`isContested`, flagged 🔥 in the UI) clears **above** formula value — so a sought-after star drains your bank and money finally bites (verified: an 84-OVR FA drew 13 rivals, a hungry rising club bidding 25% over asking; a 59-OVR fringe player drew none and signed at asking). `acquireAt(e, price)` generalises the old `acquire` to pay the winning bid. This is the **exact resolution the Phase-2 server runs on real bids** — single-player just fills the other seats with AI bidders. Pure/deterministic; the engine never sees it, so seed 42 is byte-identical. **The market is also LIVING** (`resolveAiMarket`, each match-day in `resolveDay`): a couple of motivated AI clubs (rising/rebuilding, with cash) sign the best upgrade they can find from free agency or another club's listing — a swap (their weaker same-role player goes the other way), so the pool churns and **the gems get snapped up** (verified: ~6 of the top 8 free agents signed by AI within one season). That's the urgency — spot a free agent and bid before a rival takes him. Bounded per day, deterministic (no rng beyond the existing restock). **Wages are market-linked** (`playerWage(p, patch?)` — a buffed-agent main commands more) and a built HQ charges **recurring upkeep** (`facilityUpkeep`/`academyUpkeep`, ~$13k/season fully maxed, a ledger line) — so income vs expenses is a real loop (win funds the next season, finish low or over-build and you bleed; a mid club ~breaks even). The web store reduces every move — your buy, your sale, AI churn — to one pure `trade(buyerIdx, sellerIdx, playerId)` helper (it also tracks **every club's balance**, settles them all each off-season, and runs `resolveListings()` each match-day so a player you list can sell mid-season). The whole resolution is the shape the Phase-2 server worker will run on real bids.
- `finance.ts` — club **finances** (the between-seasons economic pressure). `playerWage` is convex in `overall` (stars are dear, ~50–80% of income for a good club), `seasonIncome(rank,n)` is a sponsor cheque + placement prize, `settleSeason(team,rank,n,season)` returns the ledger the HQ adds to the balance. Tuned so a strong season funds the next and an overspending club that finishes low **bleeds** (a top squad finishing last nets ~−$6k). Pure; an economy balance pass is a Phase-6 thing. **Contracts are in** (the lasting cost of a signing): `Player.contract?: { wage, years }` is a wage **LOCKED at signing** for a term (additive/optional — undefined falls back to the market `playerWage`, so the engine sample and CLIs are byte-identical). `contractWage(p, patch)` is what you actually pay (the locked wage if any), `squadWageBill` now sums it; `demandWage` is what he'd re-sign for (current market — a raise for an improved youngster, a cut for a faded vet); `newContract(p, patch, years=CONTRACT_YEARS=3)` cuts a fresh deal. The store seeds your roster with staggered terms, sets a fresh deal on every signing/promotion, ticks `years` down each off-season (`processContracts`), and a player who hits 0 **unrenewed walks to free agency for nothing** (a "use it or lose it" banner; roster holes filled by the shared `fillRoles`). `renewPlayer(id)` re-signs at the current market wage. So overpaying for a player who then declines is a multi-season cost (the wage is locked until it expires or you sell him — the buyer inherits the deal). The squad screen shows each deal (`1y · $2.2k/y`, gold when expiring), a `renew` button on final-year players, and the total wage bill. AI clubs' wages still float (no contracts → market rate). **AI free-agency waves are in** (`resolveAiFreeAgency`, each off-season): a financially **strained** AI club (bank < $5k — it can't meet its earners' demands) loses its **priciest player** (a real star walks to the board), while a healthy club occasionally lets a fringe deal lapse; both land in the free-agent pool (`refreshMarket` folds the wave in, handles de-duped), and the club backfills so it stays at five. Bounded (≤1 per club), deterministic. So at season roll a wave of proven players — and the odd 80-OVR star a bleeding club couldn't keep — hits your market (verified: 5–15 released/season, headlined by 76–80-OVR players, every club intact). A banner headlines the wave; grab them in the Market. Engine-invisible, so seed 42 is byte-identical. (Modelled as a behavioural rule rather than per-player AI contract state — full AI contracts/locked wages are a deeper Phase-2 item.)
- `scouting.ts` — **potential behind fog** (DESIGN §4.1/§5.3), the piece that makes a young signing a *gamble*. The manager never sees a player's true ceiling — only `scoutedPotential(p, owned)`: the true `potentialOverall` biased by a deterministic per-player FNV-1a `noise` scaled by `(1 − confidence)`. `scoutConfidence` rises with age (`(age−15)/13`, a realised ceiling is clearer) and with ownership (+0.26, your staff watch them daily), clamped 0.15..0.97 — so an 18-year-old free agent is the foggiest read on the board and your own veteran the clearest. `scoutedStars` is the 1–5 UI rendering, and `scoutedRange(p, owned)` is the **ceiling band** the UI shows (roster `CEIL 70–90`, market under the stars) — wide for an unresolved prospect (real plasticity `potVar` + observation error), tight for a settled veteran, so the gamble is legible. **Potential is per-SKILL, not a lump**: the engine already grows each attribute toward its OWN ceiling (`Player.potential` is per-attribute), and `scoutedAttr(p, attr, owned)` exposes that — the true per-attribute ceiling fogged with its OWN noise (`noise(id:attr)`), so a player's aim ceiling can read clear while his utility ceiling stays murky. The roster's attribute bars render it as a faint ghost-fill + tick to each skill's scouted ceiling (`AIM 71↗81`), so a spiky prospect (elite entry ceiling, capped utility) is legible and role-fit is a real read — not "68 potential" as one number. **Scouting is a paid INVESTMENT, not free knowledge** (the store): you commission reports on a player you own or intake (`scoutPlayer(id)`, cost `1500 + level·1500`, up to `SCOUT_MAX`=3 levels), and each level adds confidence (`scoutConfidence`/`scoutedRange`/`scoutedAttr` take a `scoutLevel`, default 0 → byte-identical for the CLIs) — clearing the observation fog on his ceiling (the residual band is real `potVar` plasticity, irreducible until he develops). **The flip**: `playerValue(p, patch, scoutLevel)` carries a **risk discount** on the potential premium when unscouted (a buyer won't pay full for an unproven prospect) that scouting **removes** — so a report reliably *lifts* sale value (monotonic, never lowers it) and the report transfers on sale. A high-ceiling academy intake (free) scouted then sold is a top club's talent-trading arm — but only the genuine gems clear the scout cost, so you scout the promising ones and flip the gods you don't need (verified: a true-88-potential intake reveals +$25k; a mediocre one barely moves). The roster + academy show a `scout $1.5k` button with level pips; the consensus value (rivals' read) stays fogged. Pure (hash noise, no rng), engine-invisible, so seed 42 is byte-identical. **The fog is load-bearing on price**: `market.ts#playerValue` prices off `scoutedPotential(p, false)` (the *market consensus*, fogged), never the truth — so the board's mispriced gems are exactly the kids whose true ceiling sits outside consensus, and the value never leaks the answer. Pure (no rng — the noise is a hash of the id), so it doesn't perturb the world; the match engine ignores it, so seed 42 is byte-identical.
- `meta.ts` — the **living meta** (DESIGN §7). `PatchState.agentTier` (agent → ~0.85..1.15 multiplier) is the patch; `fullPatch(base, allAgents)` gives every agent a tier, and `patchMeta(prev, rng)` rolls a new one each off-season: ~3 buffs, ~3 nerfs (a Fisher–Yates shuffle picks the touched agents), the rest mean-revert toward 1.0, returning the new patch **and** the notable `MetaChange[]` for the patch-notes feed. The tier feeds two places: `playerValue(p, patch)` multiplies by `0.55 + tier·0.45` (a buffed agent's mains are dearer — specialists track the meta), and `buildInput` threads the live `patch` into every fixture so matches reflect it too. Deterministic (the roll is seeded `seasonSeed ^ season·0x27d4eb2f`). The sharp owner reads the patch and trades on it before values catch up.
- **Roster depth + lineup (the store, not the world pkg).** A `Club.team` is *exactly five* (the engine contract). Depth lives in the web store: `myRoster` (≥5) is your full squad and the matchday five is **derived** — `startingFive(roster)` takes the best `overall` per comp slot (duelist×2, initiator/controller/sentinel×1, IGL = the starting sentinel). A buy **adds** to `myRoster` (no forced drop); `canSell` blocks any sale that would break a valid five. **Manual lineup override**: `forcedStart`/`forcedBench` (id sets) let you `startReserve`/`benchStarter` against the auto-pick — `canBench` requires another same-role player to cover, and `startingFive` falls back to a benched player rather than ever fielding fewer than five. Depth never reaches the engine (the derived five is what's fielded), so the match contract and determinism are untouched — this is the elegant bit.
- The web app reads all of this through one **store** (`apps/web/src/world.ts`, `useWorld()`) shared by the HQ/Season screen and the Tactics Editor. Your club gets two manager overlays the AI clubs don't — an authored **comp** (`myComp`) and authored **tactics** (`myTactics`) — both injected into your fixtures via `buildInput` (it clones them so the engine gets plain objects). The editor's team 0 IS your club: its dials + authored plays write straight to `myTactics`, so what you tune is what your club runs in real fixtures; team 1 is your next opponent, edited locally (non-persistent). `ROLE_AGENTS` (exported from `clubs.ts`) feeds the comp picker. **World rankings** (`Rankings.vue`, an HQ tab) rank all `N` clubs cross-division by two lenses — **Power** (`squadRating`) and **HQ** (`infraLevel`) — each row showing division, lifecycle stage chip, OVR and HQ pips, your club pinned even when outside the top 25; read together they tell you who's strong now vs who's built to last (a high-power/low-HQ club is a dynasty about to fade — and the lifecycle market means its veterans are on the board to raid).
- **Career persistence** is a thin localStorage layer in the store: a debounced `watch` over the mutated refs writes a `snapshot()` to `ace.career.v2`, and `hydrate()` restores it on load **before** the autosave watcher is wired (so restoring doesn't re-save). The schedules aren't stored (pure `divisionSchedule` over each tier's `division` map, regenerated); Sets/Maps round-trip via arrays; a `{v, n}` guard ignores a stale/incompatible save (bump `v` when the snapshot shape changes — the division refactor did). It works because the store updates refs **immutably** (reassign, never mutate-in-place), so a shallow watch catches every change — keep that invariant or autosave misses edits. It's a pure persistence concern: the engine, determinism, and the world package are untouched (seed 42 byte-identical).
- **Don't** import `loadNavmesh` into anything the web bundles; the world CLI uses the same relative `../../maps/src/load.js` trick the engine CLI does.

## The server tick core (`@ace/server`) — Phase 2 begins

`apps/server` is the persistence + scheduling layer the async-PvP world runs on (`docs/PHASE2.md`). It owns **no** simulation math — it loads a world, calls the pure `@ace/world` functions, and persists. The two pieces in:

- **The persistence boundary** (`store.ts`): a `WorldStore` interface — a world snapshot, the season's `fixture` rows, and a `tick_log` (the idempotency key `unique(world, season, day, kind)`) — mirroring the Postgres §5 tables. A `MemoryStore` implements it so the whole tick loop runs headless; a `PgStore` (same interface) is the mechanical follow-up, and **no resolution code changes** when it's swapped in. `loadWorld` deep-copies out (a row read), so callers can't mutate stored state.
- **The tick worker** (`tick.ts`): `runTick(store, id, opts?)` resolves the world's **current match-day** (idempotent — guarded by `tick_log`, a retried/crashed job never double-resolves) or, when the season's match-days are exhausted, rolls the season over (`advanceWorld`: playoffs → settle → develop → patch → promote/relegate). Match-days are sequential (economy/dev carry); the fixtures within a day come from the pure core. **Relevance-scoping is in**: pass `{ full(division), navOf }` and the tick **full-sims** the watchable divisions with the real engine (`forks:0`, via `sim.ts`'s `fullSimResolver` → `simulateMatch`) and quick-resolves the dormant rest, persisting the `input_snapshot` per watchable fixture (`nav.ts` loads the navmesh server-side the same relative-import way the CLIs do). `pnpm run server` proves all of it headless: a 110-club / 11-tier world ticks day-by-day across seasons, **deterministic** (two independent runs byte-identical), **idempotent** (a retried tick is skipped, fixtures unchanged), and the **watch loop** holds — the Premier is engine-simmed (a real Valorant scoreline) and re-simming a stored snapshot reproduces the score **byte-for-byte** (the client re-sims to watch; the server ships a few KB).

The seam both runtimes share is **`resolveSeasonDay(world, day, devRng, opts)`** in `@ace/world/state.ts` — one match-day's fixtures + that day's in-season development, the fixture `resolve` injectable (quick-resolve default; the server will full-sim watched divisions). `simulateSeason` loops it with one season-long `devRng` (so `pnpm world` stays **byte-identical** to before the extraction), while the day-granular runtimes (the store, the server tick) call it once per tick with a per-`(season,day)` seeded rng (a tick can't hold an rng across persistence — both are reproducible, this is the server's canonical stream). - **The live window / result embargo** (`live.ts`): the engine resolves a match instantly, but a match scheduled for 8pm must **play out live** and its result stay **sealed until the broadcast finishes** (the "no spoilers until it's over" rule). Each fixture carries a `kickoffAt` + a **fixed** `broadcastSecs` → `revealAt`; `publicView(fixture, now)` is spoiler-safe by construction (before reveal: **no score, no snapshot** — so a client can't re-sim ahead; only the live position), and `liveMatchState(timeline, frac)` gates a re-simmed timeline to the live position (running score from *completed* rounds only, never the final, until `frac` hits 1 — everyone synced). At `revealAt` the row flips `resolved` and the snapshot + score go public (replay reverts to the cheap client path). Fixed duration is deliberate: a stomp and a thriller take the same slot, so the duration leaks nothing. `pnpm run server` proves it: a Premier match sealed through its window (running score 0–0 → 12–7), the final 13–7 released only at reveal. (Standings count `resolved` fixtures only, so the table never moves mid-broadcast.)

- **A runnable live-broadcast HTTP server** (`http.ts`): the pure cores above are now wrapped in an actually-running server — minimal `node:http` + **SSE**, zero new deps (the NestJS version exposes the same shapes; this proves the contract end to end over the real wall-clock). `startLiveServer({ seed, broadcastSecs, clock? })` boots a world, ticks day 0 with the Premier full-simmed + a live `kickoffAt`/`broadcastSecs`, re-sims each watchable fixture once and **caches the timeline as the live source**. Three endpoints, all gated by `live.ts`: `GET /fixtures/:s/:d/:slot` → `publicView` (spoiler-safe — SEALED during the window), `GET /fixtures/:s/:d/:slot/replay` → the snapshot but **425 until resolved** (a client can't pull it early to re-sim ahead), and `GET /live/:s/:d` → an **SSE match-center** streaming a frame/sec for the day's watchable fixtures (running score from completed rounds, current round, `frac`, status), closing on `event: done` when all resolve. `pnpm run server:live` (→ `http-demo.ts`) boots it on a short window and acts as its own client: verified the result stays SEALED + replay 425s mid-broadcast, the SSE running score ticks `1–1 → 12–7` synced to the clock, and at reveal the score + snapshot go public + replay 200s with the full snapshot. The injectable `clock` keeps it deterministic/testable; the real default is `Date.now()/1000`. This is the transport seam the WS gateway/NestJS controllers will mirror — the gating logic lives in the pure `live.ts`, so the framework only marshals it.

- **The ownership overlay** (`@ace/world/owner.ts` + `apps/server/src/owner.ts`) — humans are a **sparse, shifting layer on an always-full world** (DESIGN §6, PHASE2 §4). The deterministic generator fills every slot with an AI club; a real owner is just `WorldClub.owner` flipping `null↔account`. The pure `WorldState` transforms live in `@ace/world` (`claimClub`/`revertClub`/`setClubPlan`, with `clubOf`/`planOf`/`ownedClubs`); the server wraps them load→transform→save (`claim`/`revert`/`savePlan`/`myClub` — the Pg version is the same transforms in a row UPDATE). Two invariants are enforced at claim: **one owner per club**, **one club per account**. The load-bearing rule is **every club ALWAYS has a competent plan the tick can grab** (`(tactics, comp, lineup)`): an AI/ghosting club runs its generated tactics + comp and the **derived best five**, a human authors theirs. `lineup` (an owner's explicit five) is **additive/optional on `WorldClub`** — undefined derives `startingFive`, so generated worlds + seed 42 are **byte-identical** — and `planFive(c)` fields an explicit lineup only when it's a `validFive` drawn from the roster, **falling back** otherwise, so a stale/invalid saved lineup can never break the always-field-a-five rule (defense in depth alongside `setClubPlan`'s write-time validation). On **revert the plan persists** (the AI keeps fielding the last saved five — the world stays structurally complete). `clubTeam` now routes through `planFive` (byte-identical when no lineup is set). `pnpm run server` proves it: claiming the Premier home club then authoring its read/tempo makes the **full-sim snapshot carry the authored tactics** (the human's plan reaches the engine via `fullSimResolver`→`buildMatchInput`), a second claim is blocked, a bad lineup rejected, revert returns it to AI with the plan intact, and every club still fields a valid five. Auth — *which* account may call these — is the HTTP layer's job (step 3); the engine never sees ownership, so seed 42 is untouched.

The `MAP_POOL` + `fixtureMap` (the curated map rotation) now live canonically in `@ace/world` (the web store re-exports them) so the store and the server assign the same map to the same fixture. The engine, the timeline contract, and seed 42 are **untouched** — Phase 2 is persistence + identity + scheduling + fan-out, not a sim rewrite. Still to come (see `docs/PHASE2.md` §14): the `PgStore` + migrations, self-owned auth, wiring the proven re-sim-to-watch endpoint into the web viewer, the `(tier,grp)` fan-out, and the NestJS HTTP/BullMQ wrappers (this `node:http` slice is the shape they formalize).

## A settled contract decision (don't relitigate by accident)

Rendering vision needed facing in the timeline. The decision made: expose **only `move.hold`** — the unit heading an agent looks down once it reaches the end of its path. Facing *while moving* is the path's own direction, so a consumer reconstructs facing at any `t` from `path` + `arrive` + `hold` (see `facingOf()` in the viewer, which mirrors the engine's `facingAt()`). This was chosen over a per-tick facing track because the engine doesn't model look-arounds — sampling would just store a function the viewer can already derive. It's additive, so `version` stayed `1`. If you ever add genuine mid-path look mechanics, that's when a sampled track earns its keep — and its own `version` bump.

The viewer fetches `apps/web/public/<map>.navmesh.json` (emitted by `pnpm navmesh` alongside the engine's copy) and reuses the engine's exact LOS sampling to clip cones, so what you see matches what the engine resolved. Don't write a second raycaster.

## Tuning knobs (gameplay feel, not correctness)

These shape how lethal getting caught off-guard feels; expect to dial them after watching matches back. Keep them named constants, not magic numbers scattered in logic:

- `FOV` (cone half-angle, ~60°) — how much peripheral awareness an agent has.
- `FIRST_SHOT` — the edge for seeing an unaware enemy first; the single biggest lever on backstab/retake lethality.
- `SMOKE_R` / `SMOKE_R_UTIL`, `SMOKE_DUR` / `SMOKE_DUR_UTIL` — smoke size/duration and how hard they scale with utility; the bigger lever on how much space utility buys.
- `PULSE_R` / `PULSE_R_UTIL`, `PULSE_DUR` / `PULSE_DUR_UTIL` — recon/flash reach and window; the lever on how decisive entries are.
- `TRAP_R` / `TRAP_R_UTIL`, `TRAP_DUR` — sentinel flank-trap reach and how long it stays armed; the lever on how hard a lurk/flank is punished (and how much a sentinel is worth).
- `TRAP_SLOW` — round-fraction an enemy is delayed crossing a trap (the denial half of the trap); bigger = a tripped lurk/flank arrives further out of position. The first movement-affecting ability lever.
- `FORM_SWING` — match-night form band (± duel edge per player). Bigger = more star/dud variance night to night; keep it fair and legible, never a mugging.
- `HOLD_BONUS` + the defender rotation speed (`arriveTime(path, 0.6)`) — together the lever on how hard a wrong defensive read is punished; the heart of the tactics mind-game. Bigger hold / slower rotation = reads matter more.

To re-balance or measure a tuning change, an A/B is easy: gate utility generation, or set every non-utility attribute equal across two rosters and vary only `utility` to confirm the high-utility side wins (~58% of matches at 92 vs 18).

## Conventions

- Monorepo: pnpm + turbo. Packages are consumed as source via path mapping (`@ace/shared`, `@ace/maps`, `@ace/engine`) — tsx runs the engine, Vite bundles the app — so packages have no separate compile step; their "build" is a typecheck (`tsc --noEmit`). Don't add `rootDir`/`outDir` emit back to them, and don't commit `.js`/`.d.ts` next to `.ts` source (the web build is `vue-tsc --noEmit && vite build` specifically to avoid emitting those).
- Commit artifacts that make a cold clone work: the committed sample `apps/web/public/timeline.json` and `packages/maps/data/*.navmesh.json` are intentional so `pnpm install && pnpm dev` works without running the engine first. Regenerate them when their inputs change.
- Before opening a PR / finishing a task: `pnpm typecheck` green, `pnpm sim` deterministic across two runs and complete across several seeds, `pnpm build` green.
- TypeScript strict is on (incl. `noUnusedLocals`) — no dead variables.
